## 一、已补齐（10-29 清单 → 现状）

两份归档文档中的 P0/P1 清单绝大多数已落地，README 的「路线图」一节 30+ 项全勾，包括：

- 模块注册表 / 存储抽象（local/s3/cos）/ 安装向导 / 最小化 compose / 演示数据 / 部署体检
- 会话管理（登录设备 / 强制下线）+ 管理员强制 2FA + 登录图形验证码
- 写操作幂等 / 数据权限（本人/本部门/全部）/ 字典管理 / 岗位目录
- 统一回收站 / 待办中心 / 工作台 / 全局命令面板（Ctrl+K）/ 暗色跟随系统 / 移动端适配
- 审计字段级 diff（敏感值掩码）/ 声明式导出（CSV/XLSX）/ 用户批量导入 / 邮件与消息模板
- 登录日志 / IP 黑名单 / API 统计 / 错误日志 / 指标快照 / 敏感词库 / 密码与会话策略
- 代码生成（表内省 + 前端页面骨架 + INTEGRATION 接线）/ 版本升级 / 备份管理

## 三、定位决策（建议明确写进「已知限制」而非实现）

- **内容多语言（按 locale 存多份内容）**：Directus/Strapi 的核心能力，但与本项目「中文内容运营」定位冲突。明确不做的边界写清楚，比做一半好。
- **内容版本历史（revision timeline）**：已有审计 diff + 回收站覆盖 80% 场景，不单独立项。

## 四、明确不补（2026 榜单的卖点，维持边界）

多租户 SaaS、工作流引擎、低代码表单/页面设计器、积木报表/大屏、多数据库方言适配、插件市场——yudao/JeecgBoot 靠这些堆功能，但每一项都是独立的长期产品。本项目保持「中文内容中台」边界；这七件事在 10-29 对标文档 §五 已有完整论证，依然有效。

## 五、建议的开工顺序

1. **#3 性能基线**（1-2 天）：`scripts/bench.py` + N+1 守卫测试 + 慢查询打点——最快让 README 的「工程能力」表有数字可引。
2. **#1 PAT + Webhook**（3-5 天）：补齐开放 API 的凭据与事件出口，是从「能跑的后台」到「能被集成的平台」的分水岭。
3. **#2 OpenAPI→TS**（1 天）：`openapi-typescript` 接入 CI，删手写 types。
4. **#4/#5/#6 安全三小件**（各 0.5-1 天）。
