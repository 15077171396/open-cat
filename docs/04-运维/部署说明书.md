## 1. 架构与组件

### 1.1 整体架构

```
                    ┌─────────────┐
   用户 ──:80 ─────►│   nginx     │  前端静态托管 + 反向代理
                    └──────┬──────┘
                           │
        ┌──────────────────┼──────────────────┐
        ▼                  ▼                  ▼
   /admin/→SPA        /→SPA              /api/
        │                  │                  │
        │  (静态文件)       │                  │
        ▼                  ▼                  ▼
   /usr/share/nginx/html               ┌──────────────┐
                                       │  app (8000)  │  FastAPI + Gunicorn (2 workers)
                                       └──────┬───────┘
                                              │
                    ┌────────────┬────────────┴────────────┐
                    ▼            ▼            ▼
               ┌────────┐   ┌────────┐   ┌──────────┐
               │ mysql  │   │ redis  │   │ scheduler│
               │  8.0   │   │  7     │   │ (定时任务)│
               └────────┘   └────────┘   └──────────┘
                    ▲            ▲
                    └──── 数据卷持久化 ────┘
```

### 1.2 服务清单

| 服务 | 镜像来源 | 作用 | 对外端口 | 数据持久化 | 内存上限 |
| --- | --- | --- | --- | --- | --- |
| `nginx` | 本地构建（Dockerfile.nginx，内含双前端构建） | 前端入口 + 反向代理 + 爬虫分流 | 80 | `nginx.conf` 只读挂载 | 128m |
| `prerender` | 本地构建（prerender/Dockerfile） | SEO 预渲染：爬虫 UA 分流至此，Chromium 渲染 SPA 完整 HTML（结果缓存 Redis） | 仅内部 | - | 1g |
| `app` | 本地构建（backend/Dockerfile） | FastAPI 后端 API | 仅内部 | `./logs`（结构化日志落宿主机）+ `./backups`（**只读**，供「系统状态」卡观测备份年龄） | 768m |
| `scheduler` | 与 app 共用镜像（`command: python -m scheduler.tasks` 覆盖默认启动） | 定时任务（8 个注册任务，配置表驱动，运维见 9.4） | -（无健康检查，靠日志与后台任务页观测） | `./logs`（与 app 共享） | 192m |
| `migrate` | 与 app 共用镜像 | 数据库迁移（一次性，跑完退出；**启动链咽喉**：app/scheduler 等它成功才启动） | - | - | - |
| `mysql` | mysql:8.0 | 关系数据库 | 仅绑 127.0.0.1:3306 | `mysql_data` 卷 | 1g |
| `redis` | redis:7-alpine | 缓存 + 限流计数 + 令牌吊销 + 预渲染结果缓存 + 调度心跳/命令队列 | 仅内部 | `redis_data` 卷 | 640m |
| `umami` | umami 官方镜像 | 开源自托管访问统计（站点埋点数据） | 仅内部 | -（Umami v3 数据全在 PostgreSQL） | 512m |
| `postgres` | postgres 官方镜像 | **仅供 umami 使用**，与应用库完全隔离 | 仅内部 | `umami_pg_data` 卷 | 256m |

> 各常驻服务的 `mem_limit` 是**硬上限而非预留**，合计约 4.5G 高于物理 4G 是有意为之——
> 内存紧张时由内核按上限逐个 OOM，只死一个服务而不是拖垮整机（见 14 章排障）。

### 1.3 路由规则

| URL 路径 | 转发目标 | 说明 |
| --- | --- | --- |
| `/` | nginx 本地 `/usr/share/nginx/html` | 用户前台 SPA |
| `/`（爬虫 UA） | `prerender:3000` | 百度/360/搜狗/必应等爬虫 → 预渲染完整 HTML（Googlebot 除外，其自带 JS 渲染） |
| `/admin/` | nginx 本地 `/usr/share/nginx/html/admin` | 管理后台 SPA |
| `/api/` | 后端 `app:8000` | 后端 API 反向代理 |
| `/sitemap.xml` | 后端 `/api/v1/sitemap.xml` | SEO 站点地图（数据库动态生成）。URL 未超单文件上限时为单份 `urlset`，超过后自动改为 `sitemapindex` |
| `/sitemap-{n}.xml` | 后端 `/api/v1/sitemap-n.xml` | SEO 站点地图**分片**：单文件上限 45000 条 URL，越界返回 404 |
| `/robots.txt` | nginx 本地静态文件 | 爬虫抓取规则 |
| `/healthz` | nginx 直接返回 200 | 负载均衡 / 编排探活（不经过后端） |
| `/api/v1/health` | 后端 | 浅健康检查，不触碰外部依赖 |
| `/api/v1/health/deep` | 后端 | **深度探活**：实探 MySQL + Redis，**并校验 MySQL 会话时区为 UTC**；故障或时区非 UTC 返回 503（详见 [12.2](#122-探活uptime-监控)） |

### 1.4 启动依赖顺序

```
mysql (healthy) ──► migrate (completed) ──► app (healthy) ──► nginx
                                   └──────► scheduler
redis (started) ──┬────────────────────────► app
                  └────────────────────────► prerender (started) ──► nginx
umami (started) ──────────────────────────► nginx
```

- `migrate` 是一次性容器，执行 `alembic upgrade head` 后退出
- `app` 依赖 `migrate` 成功完成（`service_completed_successfully`）才会启动
- `nginx` 依赖 `app` **健康检查通过**、`prerender` 与 `umami` **已启动**（`service_started`，刻意不要求 healthy——预渲染或统计挂了只少功能，不能把主站一起拖下水；nginx 侧对预渲染有 SPA 壳回退）
- `prerender` 的 Chromium 按需启动（首个爬虫请求才拉起浏览器），健康检查仅探 HTTP 服务

## 2. 服务器与环境要求

### 2.1 硬件最低配置

| 资源 | 最低 | 推荐 |
| --- | --- | --- |
| CPU | 2 核 | 4 核 |
| 内存 | 4 GB | 8 GB |
| 磁盘 | 20 GB SSD | 50 GB SSD |
| 带宽 | 5 Mbps | 10 Mbps+ |

> 说明：MySQL 8 + Redis + Node 构建前端较吃内存，4G 是底线。镜像构建时峰值内存约 2G。

### 2.2 操作系统

推荐 64 位 Linux，已验证发行版：

- Ubuntu 20.04 LTS / 22.04 LTS
- Debian 11 / 12
- CentOS 7（需较新内核）/ CentOS Stream 8/9
- Rocky Linux 8/9

### 2.3 软件依赖

- Docker Engine 20.10+
- Docker Compose v2+（`docker compose` 子命令形式）
- git（拉取代码）
- 文本编辑器（vi/nano）

### 2.4 网络

- 服务器安全组 / 防火墙放行 **80 端口**（默认）
- 若使用自定义端口，放行对应端口（见 `.env` 中 `NGINX_PORT`）
- 服务器需可访问公网（拉取镜像、调用 DeepSeek API、上传腾讯云 COS）

### 2.5 服务器初始化建议

```bash
# 更新系统
sudo apt update && sudo apt upgrade -y        # Debian/Ubuntu
# 或: sudo yum update -y                       # CentOS/RHEL

# 创建非 root 部署用户（推荐）
sudo useradd -m -s /bin/bash deploy
sudo passwd deploy
sudo usermod -aG sudo deploy                   # 赋予 sudo 权限
su - deploy

# 设置时区（可选）
sudo timedatectl set-timezone Asia/Shanghai

# 关闭 swap（Docker 推荐，可选）
sudo swapoff -a
# 永久关闭: 注释 /etc/fstab 中的 swap 行
```

## 3. 安装 Docker

### 3.1 一键安装（推荐，所有发行版通用）

```bash
curl -fsSL https://get.docker.com | sh
```

### 3.2 启动并设置开机自启

```bash
sudo systemctl enable --now docker
sudo systemctl status docker          # 确认 active (running)
```

### 3.3 将当前用户加入 docker 组（免 sudo）

```bash
sudo usermod -aG docker $USER
newgrp docker                         # 立即生效（或重新登录）
```

### 3.4 验证安装

```bash
docker --version
# 预期: Docker version 24.x.x 或更高

docker compose version
# 预期: Docker Compose version v2.x.x 或更高

docker run --rm hello-world
# 预期: 出现 "Hello from Docker!" 字样
```

### 3.5 配置镜像加速（国内服务器强烈建议）

```bash
sudo mkdir -p /etc/docker
sudo tee /etc/docker/daemon.json <<-'EOF'
{
  "registry-mirrors": [
    "https://docker.m.daocloud.io",
    "https://dockerproxy.com",
    "https://docker.nju.edu.cn"
  ],
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "50m",
    "max-file": "3"
  }
}
EOF
sudo systemctl daemon-reload
sudo systemctl restart docker
```

> `log-opts` 限制容器日志大小，避免磁盘被日志撑爆。

## 4. 获取项目代码

### 4.1 方式一：git clone（推荐）

```bash
cd ~
git clone <你的仓库地址> ai-cat
cd ai-cat
```

### 4.2 方式二：上传代码包

若暂无 git 仓库，可在本地打包后上传。

> 🚨 **打包前必读（2026-10-10 安全修复）**
> 项目根目录与 `backend/` 下**存在 `.env`（含 `SECRET_KEY` / `DB_PASSWORD` /
> `REDIS_PASSWORD` / `DEEPSEEK_API_KEY` / `COS_SECRET_KEY` / `SMTP_PASSWORD` 等真实密钥）**。
> 一旦被打进压缩包上传，随后 `docker compose build` 会把它 `COPY` 进**镜像层**——
> 之后即使删除文件也仍留在历史层，任何拿到镜像的人都能读出。
>
> ⚠️ **`tar` 的排除必须用正斜杠 `/`，不能用反斜杠 `\`**：
> `--exclude=backend\venv` 在 GNU tar 下**不会生效**（`\` 是转义符不是路径分隔符），
> 会把整个 `venv/` 与 `.env` 一起打进去且**不报任何错**。已实测验证。

#### ✅ 最推荐：用仓库自带的打包脚本

```bash
bash scripts/pack-deploy.sh              # 输出 ./ai-cat-deploy.tar.gz（约 2.8MB / 579 条目）
bash scripts/pack-deploy.sh /tmp/x.tar.gz  # 也可指定输出路径
```

它把「该带什么、不该带什么」写死成代码，不再依赖每次手工敲 `--exclude`：

| 维度 | 做法 |
|---|---|
| 数据来源 | `git archive HEAD` —— 只含**已提交**内容，未跟踪的 `.env` / `venv` / `node_modules` 天然不会进去 |
| 换行符 | `git archive` 导出 blob 内容，配合 `.gitattributes` 的 `* text=auto eol=lf` **一律 LF**（见下方事故记录） |
| 白名单 | 只有 `docker-compose.yml` / `deploy.sh` / `Dockerfile.nginx` / `nginx.conf` / `.dockerignore` / `.env.example` / `backend` / `frontend` / `admin-frontend` / `prerender` / 4 个服务器侧脚本 |
| 排除 | 8 张未被引用的设计源图（≈4.8MB）、`backend/tests`（≈970KB）、`backend/pytest.ini` |

脚本自带**三项自检**，任一不过直接退出非 0：

1. 不得出现 `node_modules` / `venv` / `.git` / `__pycache__` / `dist` / `logs` / `backups` / 真实 `.env` / `*.pyc`；
2. 部署必需文件必须在（compose、`deploy.sh`、`Dockerfile.nginx`、`nginx.conf`、两个 Dockerfile、`backup_mysql.sh`）；
3. 所有 `.sh` / `Dockerfile*` / `*.conf` / `*.yml` 必须是 **LF** 换行。

> 🚨 **CRLF 事故（2026-10-21）**：手工 `tar -czf` 打工作区，在 Windows 上
> `core.autocrlf=true` 会把 `.sh` 转成 CRLF，服务器执行时直接报：
> ```
> deploy.sh: line 10: $'\r': command not found
> : invalid option nameet: pipefail
> ```
> 已上传的旧包临时救法（不用重传）：
> ```bash
> find . -maxdepth 3 -type f \( -name '*.sh' -o -name 'Dockerfile*' -o -name '*.conf' -o -name '*.yml' \) -exec sed -i 's/\r$//' {} +
> ```
> 另：**不要用 `grep -q $'\r'` 判断 CRLF** —— Git Bash 会把参数里的 CR 吃掉，
> 把 CRLF 文件误判成 LF。用 `tr -cd '\r' < 文件 | wc -c`。

**方式 A（推荐，前提是本地有 git 仓库）**——只打包已提交的文件，
未跟踪的 `.env` / `venv` / `node_modules` 自动被排除，无需手写排除规则：

```bash
# 本地（Windows PowerShell）
cd e:\wxl-project\ai\trae\ai-cat
git archive --format=tar.gz -o ai-cat.tar.gz HEAD
```

**方式 B（无 git 仓库时的文件系统打包）**：

```bash
# 本地（Windows PowerShell）
cd e:\wxl-project\ai\trae\ai-cat
tar -czf ai-cat.tar.gz `
  --exclude=.git --exclude=node_modules --exclude=venv --exclude=.venv `
  --exclude=.env --exclude=dist --exclude=__pycache__ --exclude=.pytest_cache `
  --exclude=logs --exclude=backups --exclude=*.tar.gz `
  --exclude=.workbuddy-ai --exclude=.trae --exclude=.agents --exclude=.mimosa `
  .

# ⚠️ 打包后务必自检（应当只列出 .env.example，且不应出现 venv/node_modules）：
tar -tzf ai-cat.tar.gz | grep -E "\.env"
tar -tzf ai-cat.tar.gz | grep -cE "/venv/|/node_modules/"
# 期望输出：仅两行 .env.example；依赖目录计数为 0
```

```bash
# 上传到服务器（scp 或其他工具）
scp ai-cat.tar.gz deploy@<服务器IP>:~/

# 服务器解压
```

## 5. 配置环境变量

即项目根目录的 `.env` 文件（由 `.env.example` 复制而来）。

### 5.1 创建 .env 文件

```bash
cp .env.example .env
vi .env
```

### 5.2 必填项详解

| 变量 | 说明 | 生成方式 | 示例 |
| --- | --- | --- | --- |
| `SECRET_KEY` | JWT 签名密钥，**≥32 字符随机串**，泄露即等于账号可伪造 | `openssl rand -hex 32` | `a1b2c3...（64 字符）` |
| `MYSQL_ROOT_PASSWORD` | MySQL root 密码，强密码（字母+数字+符号，16 位+） | 自定义或密码生成器 | `MyStr0ng#Pass2024` |
| `REDIS_PASSWORD` | Redis 访问密码，强密码 | 自定义或密码生成器 | `R3dis#S3cret!2024` |

**生成随机密钥的快捷命令：**

```bash
# 生成 SECRET_KEY
openssl rand -hex 32

# 生成强密码
openssl rand -base64 24
```

### 5.3 可选项详解

> **两层配置模型（2026-10-19 起）**：下表大部分项**不必改 `.env` 再重启**，
> 直接在后台「系统设置」里改即可 —— 后台值（`system_settings` 表）优先，`.env` 只作兜底默认；
> 后台清空该项即恢复 `.env` 的值。保存后当前进程立即生效，其他 worker 最多 60 秒跟上。
>
> - **后台可改**：免费时长、单用户 AI 限额/重试、全站 AI 上限与单价、敏感词审核、上传大小、
>   限流阈值、全文检索开关、站点根地址、百度/IndexNow 推送凭据、GitHub/HuggingFace 代理与 Token、
>   COS 凭据与域名、小程序 AppID/Secret、SMTP 邮件配置。
> - **必须留在 `.env`**：`SECRET_KEY` / `JWT_*`（安全边界）、`DB_*` / `REDIS_*`（基础设施）、
>   `CORS_ORIGINS` / `TRUSTED_PROXIES`（请求信任链）、`SENTRY_*`（SDK 只在启动时初始化一次）、

## 6. 执行部署

### 6.1 一键部署（推荐）

```bash
chmod +x deploy.sh
./deploy.sh up
```

**脚本执行流程（以 `deploy.sh` 当前实现为准）：**

1. 检查 Docker 与 Compose 是否安装
2. 检查 `.env` 是否存在，不存在则从模板创建（权限 600）并提示编辑后退出
3. 安全解析 `.env`（逐行 KEY=VALUE，不做 shell 展开），校验 `SECRET_KEY` / `MYSQL_ROOT_PASSWORD` / `REDIS_PASSWORD` 非占位符；随后检查告警通道（WATCHDOG_WEBHOOK / watchdog cron / SENTRY_DSN，只警告不阻断）并准备 `./logs` 目录（chown 到容器内 uid 10001）
4. 解析发版号 `APP_RELEASE`（`.env` → git 短号 → 时间戳兜底）
5. **给现有镜像打 `:prev` 快照**（backend / nginx / prerender），失败时有一条命令换回上一版的退路（见 10.5 C）
6. **迁移前强制备份**（`scripts/backup_mysql.sh`；备份失败即终止发版，`DEPLOY_SKIP_BACKUP=1` 可显式跳过；首次部署无运行中的 mysql 容器时自动跳过）
7. **只停应用层**容器（`app scheduler nginx prerender`，MySQL/Redis 保持运行，缩短 502 窗口），随后 `COMPOSE_PARALLEL_LIMIT=1` **串行构建** app / prerender / nginx 三个镜像（低内存防 OOM）
8. `docker compose up -d`（失败进 `diagnose` 打印容器状态与各服务日志 + `:prev` 回滚提示，并以非零码退出）
9. 门禁一（阻断）：轮询健康**最多 180 秒**：探的是 `http://127.0.0.1:80/api/v1/health`（带 `Host` 头经反代打到后端，显式比对 200——不用 `curl -f`，3xx 不算通过），不是 nginx 的静态 `/healthz` —— 后者 `return 200`，后端容器全挂时它照样绿（第五轮审查 R5-02）
10. 门禁二（阻断）：统计后台 `tj.wdmao.cn` 首页须 200（最长 120s，本地直连 + Host 头）——2026-10-14 tj 整域 500 静默上线的复盘门禁
11. 打印深度探活结果（非 200 只报错**不阻断**：Redis 故障时站点仍可服务）；门禁三（阻断）：**内容页冒烟**——五类内容各取 3 条列表→详情（tutorials 另探 `/intro`），出现 5xx 即失败（401/403 属正常权限语义）——2026-10-20 教程全站 500 事故的复盘门禁，健康探针照不见的 ORM 层 500 由它兜底
12. 清理 7 天前的悬空镜像，打印访问地址

**首次构建预期耗时：**

| 阶段 | 耗时 |
| --- | --- |
| 拉取基础镜像（python/node/nginx/mysql/redis） | 3–8 分钟（视带宽） |
| 后端 pip install | 2–4 分钟 |
| 前端 npm install + build（×2） | 5–10 分钟 |

### 9.4 定时任务后台页运维

定时任务（VIP 过期降级、百度/IndexNow 收录推送、浏览量落库、各类清理等）跑在独立的
`scheduler` 容器（`python -m scheduler.tasks`），**启停与周期不需要登服务器改代码**，
后台「系统 → 定时任务」页（`/admin/scheduled-jobs`）即可操作：

| 操作 | 入口 | 生效时机 |
|------|------|---------|
| 启用 / 停用某任务 | 列表行开关 | ⚠️ **保存成功 ≠ 已生效**：调度器每 5 秒对齐一次数据库配置，页面会据 `apply.pending` 提示「待生效」，最多 5 秒后生效 |
| 修改执行周期 | 行内编辑（每日 HH:MM 或每 N 分钟，1–10080） | 同上，5 秒内生效 |
| 立即执行一次 | 行内「执行」按钮 | **异步**：命令经 Redis 队列（`ops:jobs:commands`）投递，由调度器进程消费执行 |
| 查看是否真的在跑 | 页面「调度器状态 / 心跳」 | 调度器每 5 秒把「我按哪份配置在跑」写进 Redis 心跳（`ops:jobs:applied`，TTL 120s）；超时无心跳即判定「调度器未运行」 |

**两条必须知道的语义：**

1. **调度器未运行时「立即执行」返回 503，而不是「成功入队」**——队列里的命令没人消费，
   假装成功只会误导排障；页面会明确提示「调度器未运行」。生产上看到 503 先查
   `docker compose ps scheduler` 与 `docker compose logs --tail=50 scheduler`。
2. **改配置写的是数据库（`scheduled_job_configs` 表），不是 `.env`**——不存在「改完要重启容器」；
   反过来，`.env` 里也没有任何定时任务开关可改。

**权限**：读 `dashboard:view`，写 `scheduler:manage`（超管默认持有，其余角色需要时显式勾选）；写操作全部落审计。**不能新增/删除任务**：任务体固定在代码 `JOB_FUNCS`，新增一种任务 = 一次代码变更。任务清单与调度机制详见[项目说明](../03-开发/项目说明.md) 5.7。

**本机开发**：没有 scheduler 容器，要跑任务请双击 `scripts/start-scheduler.bat`
（等价于 `python -m scheduler.tasks`，配置热重载与立即执行行为与生产一致）。
不开它也能用后台页看状态、启停、改周期，但「立即执行」会 503——那是准确的。
⚠️ 它会真的执行任务（清理日志、降级 VIP、推送收录），**本机开发库同样会被改动**。


代码更新若包含新的 alembic 迁移，`rebuild` 时 `migrate` 容器会自动执行。如需手动重跑：

```bash
docker compose up migrate               # 单独执行迁移
docker compose up -d app scheduler      # 再启动应用
```

### 10.5 回滚

> ⚠️ **先判性质再动手**（第五轮审查 R5-D1）：回滚分「纯代码回滚」和「含迁移的回滚」两种，
> 后者**不能只回退代码**。`deploy.sh` 失败时打印的提示与本页旧版本都曾写「git checkout 上一提交
> 再 `./deploy.sh rebuild`」—— 对含改名/删列迁移的版本，这条路径会把「部分页面坏」升级成「整站起不来」，
> 因为 `app` 依赖 `migrate` 成功（`service_completed_successfully`），而旧镜像的 alembic 目录里
> **没有**新 revision，`alembic upgrade head` 会以 `Can't locate revision` 直接失败。

**C. 镜像层快速回退（首选，适用于「本次没跑迁移」或纯应用层故障）**——`deploy.sh` 发版前给三个自研镜像打过 `:prev` 快照，四条命令回到上一版：

```bash
docker tag ai-cat-backend:prev ai-cat-backend
docker tag ai-cat-nginx:prev ai-cat-nginx
docker tag ai-cat-prerender:prev ai-cat-prerender
docker compose up -d
```

> ⚠️ 若本次发版**已执行迁移**，必须先按 B 把 schema 退到旧代码认识的 head（或恢复发版前备份），
> 否则旧代码起不来（原因见本节开头）。

**A. 本次发版没动 schema**（`git log` 与 `git diff --stat HEAD~1 -- backend/alembic` 都为空）：

```bash
git log --oneline -5                    # 找到上一个稳定 commit
git checkout <commit-hash>
./deploy.sh rebuild
```

**B. 本次发版含迁移** —— 代码与 schema 是**双向锁定**的，按下面顺序做，缺一步就可能卡死：

```bash
# 1) 先确认有可恢复的时点（deploy.sh 会在迁移前自动备份；手工发版必须先自己跑一次）
bash scripts/backup_mysql.sh && docker compose run --rm migrate alembic current

# 2) 记下当前 head，回滚时要把 schema 退到「旧代码认识的那个 head」
docker compose run --rm migrate alembic current      # 例如 add_updated_at_indexes

# 3) 退 schema（-1 只退一个版本；一次发版上了 N 个迁移就要退 N 个，或用绝对 revision 名）
docker compose run --rm migrate alembic downgrade <旧代码的 head 名>

# 4) 再切代码，最后起服务
git checkout <commit-hash>
./deploy.sh rebuild
```

**已知会丢数据的回滚**（这些迁移的 `downgrade` 不是无损的，退之前必须已经在第 1 步有备份）：

| 迁移 | 回滚的代价 |
| --- | --- |
| `20261012_0038_generalize_comment_targets` | `downgrade` 会**删除** `target_type <> 'tutorial'` 的评论行（节点/资源评论），执行前会打印数量与类型分布 |
| `20261012_0040_drop_plugin_legacy_fields` | 删 `platform / version / rating / install_count` 四列；`downgrade` 只重建结构，**数据找不回** |

不确定属于 A 还是 B 时，一律按 B 处理。迁移幂等化（0038/0040 每步都带存在性判断）解决的是
「迁移中途被杀后能否原地重跑」，它**不**替代备份 —— 重跑能续上，续上不等于数据没丢。

## 11. 数据备份与恢复

> 备份脚本见 `scripts/backup_mysql.sh`。
> 本章所有操作统一走项目内脚本 `scripts/backup_mysql.sh`，**不要手写 crontab 命令**

### 11.0 一键开启自动备份（推荐，30 秒完成）

```bash
cd /opt/ai-cat            # 换成你的项目目录

# 1) 先自检：docker / .env / mysql 容器 / 磁盘 / 目录可写
./scripts/backup_mysql.sh --doctor

# 2) 装定时任务（默认每天 03:17，保留 30 天）
./scripts/backup_mysql.sh --install-cron

# 3) 立刻手动跑一次，确认真的能出文件（这一步别省，装完不验证等于没装）
./scripts/backup_mysql.sh
./scripts/backup_mysql.sh --list
```

脚本做了什么（都是手写 crontab 容易漏掉的）：

| 环节 | 处理 |
|------|------|
| 导出 | `mysqldump --single-transaction`（InnoDB 一致性快照，不锁表）+ 例程/触发器/事件一并导出 |
| 凭据 | 密码取容器内的 `$MYSQL_ROOT_PASSWORD`，**不出现在命令行**，`ps` 看不到 |
| 落盘 | 边导边 `gzip -9`，先写 `.part` 临时文件，校验通过才 `mv` 成正式备份 |
| 校验 | `gzip -t` 完整性 + 解析出的 `CREATE TABLE` 数 ≥ 10，**空库/截断文件直接判失败并丢弃** |
| 并发 | `flock` 单实例锁，cron 与手动撞车时后者跳过，不会写出两份半成品 |
| 轮转 | 默认保留 30 天，`.sha256` 一起清理 |
| 日志 | 全部落 `backups/backup.log`（cron 场景 stdout 会丢，只有文件查得到） |
| 权限 | 备份目录 `700`、文件 `600`——里面是全量业务数据 |

### 11.0.1 可调参数

```bash
BACKUP_DIR=/data/backups     ./scripts/backup_mysql.sh   # 换备份目录（默认 <项目根>/backups）
BACKUP_KEEP_DAYS=90          ./scripts/backup_mysql.sh   # 保留 90 天（默认 30）
BACKUP_CRON="17 3 * * *"     ./scripts/backup_mysql.sh --install-cron
BACKUP_MIN_TABLES=20         ./scripts/backup_mysql.sh   # 校验阈值：解析出的表数低于该值判备份无效（默认 10）
```

- **磁盘预检**：备份前检查磁盘剩余空间，默认预留 1GB（`BACKUP_MIN_FREE_KB` 可调），不足直接拒绝备份——磁盘将满时写出来的半成品比没有备份更误导人。
- **卸载定时任务**：`./scripts/backup_mysql.sh --uninstall-cron`。
- **日志**：全部落 `backups/backup.log`；cron 场景 stdout 另落 `backups/cron.log`，**两处都要看**。

> 备份目录已加入 `.gitignore`（`backups/`），**备份产物绝不能入库**。

### 11.1 手动备份

```bash
./scripts/backup_mysql.sh
```

**预期输出：** `backups/` 下生成 `ai_cat_20260801_120000.sql.gz` 与同名 `.sha256`。

### 11.2 备份校验与查看

```bash
./scripts/backup_mysql.sh --list      # 列出所有备份（名称/大小/时间）
./scripts/backup_mysql.sh --verify    # 校验最近一份是否可解压、表结构完整
./scripts/backup_mysql.sh --cron-status   # 定时任务装了没 + 最近备份是不是太旧
```

> `--cron-status` 会在最近一份备份超过 2 天时告警——**"定时任务装了但没在跑"是最常见的失效模式**，
> 建议把它加进每月巡检。

### 11.3 恢复（⚠️ 危险操作）

```bash
./scripts/backup_mysql.sh --restore backups/ai_cat_20260801_120000.sql.gz
```

脚本的三道保险：

1. 恢复前先校验备份文件（坏的备份拒绝执行）；
2. 要求手动输入**库名**确认，且非交互环境（cron/管道）直接拒绝——防止误触发；
3. 执行前自动把**当前库**另存为 `backups/pre_restore_*.sql.gz`，恢复错了还能退回。

恢复后重启业务容器，避免连接池里残留旧会话：

```bash
docker compose restart app scheduler
```

### 11.3.1 手工恢复（脚本不可用时的兜底）

```bash
docker compose exec -T mysql sh -c \
  'exec mysqldump -uroot -p"$MYSQL_ROOT_PASSWORD" --single-transaction "$MYSQL_DATABASE"' \
  > backup_$(date +%Y%m%d_%H%M%S).sql

gzip -dc backups/ai_cat_20260801_120000.sql.gz | docker compose exec -T mysql sh -c \
  'exec mysql -uroot -p"$MYSQL_ROOT_PASSWORD" "$MYSQL_DATABASE"'
```

### 11.6 清理存量孤儿数据（一次性）

收藏表与学习记录表存的是**快照**、无外键，历史版本删除内容时未清理引用，
用户「我的收藏 / 我的学习」里会留下点开即 404 的死条目。新增内容的孤儿已由
代码修复（删除内容时同事务清理引用），**存量部分需执行一次**（对应）：

```bash
# 只生成 SQL，不连库、不删数据——先人工过目
python scripts/cleanup_orphans.py                 # 打印到标准输出
python scripts/cleanup_orphans.py --counts-only   # 只要统计语句
python scripts/cleanup_orphans.py --out /tmp/orphans.sql
```

生成的 SQL 分【统计】与【清理】两段：**先跑统计确认数量符合预期，再跑清理**，
执行前先按 11.0 做一次备份。

### 11.7 离机备份（BACKUP_AFTER_HOOK）

备份默认落在项目同盘的 `backups/`——机器或磁盘故障会**同时丢掉数据与备份**。
`BACKUP_AFTER_HOOK` 把「把备份送出机器」做成一条可配置命令，不绑定任何云厂商。

在 `.env` 中填一条上传命令即可，脚本会在「本地备份已落盘并校验通过、轮转完成」之后执行，
并向它注入两个环境变量：

| 变量 | 含义 |
|------|------|
| `BACKUP_FILE` | 刚生成的 `.sql.gz` 绝对路径 |
| `BACKUP_NAME` | 文件名 |

```env
# rclone（推荐，支持 S3/OSS/COS/网盘等数十种后端）
BACKUP_AFTER_HOOK='rclone copy "$BACKUP_FILE" remote:ai-cat-backup/'
# 或 scp
BACKUP_AFTER_HOOK='scp -q "$BACKUP_FILE" backup@10.0.0.9:/data/ai-cat/'
```

**失败语义（刻意如此）**：钩子失败时本地备份依然有效，脚本整体仍按成功退出（退出码 0），
只打一条 ERROR 并写入 `backups/backup.log`——「本地备份成功」与「有没有异地副本」是两件事，
混成一个失败码会让 cron 告警失去指向。异地副本的兜底检查是看门狗的备份年龄告警（12.2.1）
与后台「系统状态」卡（12.4）。

自检：`./scripts/backup_mysql.sh --doctor` 会对「未配置离机钩子」给出告警。
注意 `BACKUP_AFTER_HOOK` 由宿主机脚本读取，**不进容器**，只写在 `.env` 即可。

## 12. 可观测性（错误监控 / 探活 / 日志）

> 告警通道的配置方法见第 12 章。
> 设计原则：**默认全部关闭**——不配置就不加载 SDK、不产生任何网络请求、不影响启动耗时。

### 12.1 错误监控（Sentry / GlitchTip）

配置后，未捕获异常与 ERROR 级日志会带堆栈上报。不配置时线上 500 只能等用户投诉才知道。

**两种后端任选**：

| 方式 | 说明 |
|------|------|
| Sentry SaaS | 官网建项目，复制 DSN |
| 自建 GlitchTip | 开源、Sentry 协议兼容，填其项目 DSN 即可，**代码无需改动**（与本项目自托管 Umami 的取向一致） |

**后端 + 定时任务**（运行时读取，重启容器即生效）：

```bash
# .env
SENTRY_DSN=https://<key>@<host>/<project-id>
SENTRY_ENVIRONMENT=production
APP_RELEASE=$(git rev-parse --short HEAD)   # 建议填：用于区分「哪个版本开始出这个错」
APP_UPDATE_REPO=owner/repo                # 可选：后台「版本与升级」检查 GitHub 最新 release；留空不联网
SENTRY_TRACES_SAMPLE_RATE=0                 # 0 = 只上报错误，不开性能追踪
```

```bash
docker compose up -d app scheduler
```

> 定时任务跑在独立容器、不经过 `create_app`，已单独初始化监控——
> **定时任务静默失败是最难发现的故障类型**，建议一并配置。

**前端**（⚠️ `VITE_*` 是**构建期**变量，改完必须重新构建镜像，否则「配了也没数据」）：

```bash
# .env
VITE_SENTRY_DSN=https://<key>@<host>/<project-id>
```

```bash
docker compose build nginx && docker compose up -d nginx
```

> 前端 DSN 会随产物下发到浏览器，这属 Sentry 的设计（DSN 仅用于投递，不是密钥）。
> 想区分前后端错误就在 Sentry 建两个项目、分别填 `SENTRY_DSN` 与 `VITE_SENTRY_DSN`；
> 前后台共用同一 DSN 也可以——后台页面路径均以 `/admin/` 开头，可据此筛选。
> 未配置时前端产物中不含该配置，SDK 单独成 chunk 且**永不下载**（入口包零增长）。

**已内置的凭据保护**（本站接口大量传递明文口令、邮箱验证码、access/refresh token，必须擦除）：

| 层次 | 措施 |
|------|------|
| ① 源头不采集 | `data_collection`：请求体 / cookie / query 参数 / 用户身份 / AI 对话输入输出 **全部关闭**；请求头走 denylist（`authorization`、`cookie` 等）。后端保留堆栈帧局部变量（变量名未混淆，对排查有价值，再由 ② 按名擦除）；**前端不采集局部变量**——产物经压缩混淆后变量名已不可读，按名脱敏必然失效 |
| ② 上报前擦除 | `before_send` 递归擦除字段名含 password / token / secret / code 等的值，并对自由文本做凭据正则——覆盖日志正文、异常描述、面包屑、**堆栈帧局部变量与源码行** |
| ③ 前端面包屑 | 直接丢弃 `ui.input` 类面包屑（登录页的明文口令在此）；`beforeSend` 丢弃请求体 / cookie / query string |

### 12.2 探活（uptime 监控）

三级健康检查，用途不同，**不要混用**：

| 端点 | 行为 | 用途 |
|------|------|------|
| `GET /healthz` | nginx 直接返回 `ok`，**不经过后端** | 负载均衡 / 容器编排探活 |
| `GET /api/v1/health` | 后端返回 `{"status":"ok"}`，**不触碰任何外部依赖** | 判断后端进程是否存活 |
| `GET /api/v1/health/deep` | 实探 **MySQL + Redis**，并做两项附加校验：**会话时区为 UTC**、**库版本 == 代码 head**；全部正常 → `200`，任一故障或校验不过 → **`503`** | **uptime 监控告警** |

```bash
curl -s http://localhost/api/v1/health/deep | python3 -m json.tool
# 正常: HTTP 200  {"code":0,"data":{"status":"ok","checks":{"mysql":{"ok":true,"ms":1.2,
#                    "utc":true,"tz_offset_seconds":0},"redis":{"ok":true,"ms":0.4}},"ts":...}}
# 故障: HTTP 503  status=degraded，且能指出是 mysql 还是 redis 不通
# 时区错: HTTP 503  checks.mysql.error = "MySQLSessionNotUTC"（会话时区不是 UTC）
# 库落后: HTTP 503  checks.mysql.error = "SchemaOutOfDate"
#          checks.mysql.schema_revision="seed_comment_permissions" / schema_head="add_admin_audit_log"
#          → 在 backend 目录执行 `alembic upgrade head`（改数据前先备份）
```

- 浅检查**刻意不探测数据库**：依赖故障时返回失败会让编排器反复重启容器，把「下游抖动」放大成「服务不可用」。
- 深度检查结果按 `HEALTH_DEEP_CACHE_SECONDS`（默认 5 秒）缓存，吸收探活的高频请求；Redis 不可用时退化为每次直连探测，判定不受影响。
- 响应只回传**异常类名**，不回传异常消息——驱动异常消息常包含主机 / 端口 / 账号等连接信息。
- ⚠️ **为什么把「会话时区非 UTC」也判成失败**：全库 naive 时间戳按 UTC 写入是本项目的**代码级约定**——统计日界（`stats_service`）、VIP 到期（`is_vip_effective`）、免费时长倒计时（`timer_service`）都直接拿 naive 值当 UTC 比较；而 `created_at` / `updated_at` 这类列由数据库 `func.now` 写入，**语义完全取决于会话时区**。一旦不是 UTC，DB 写本地时间、应用写 UTC，两者混用会**静默**产生小时级偏差（可能白送几小时权益，也可能瞬间判为耗尽）。这种「不报错但算错」的配置错误必须可见。
  排查：`SELECT @@session.time_zone, TIMEDIFF(NOW, UTC_TIMESTAMP);`。**该判定不会导致容器重启**（编排健康检查用的是 `GET /`，不是本端点）。
  ✅ **自 P2-13 起，应用在连接层就锁定了会话时区**（`app/database.py` 的 `MYSQL_SESSION_TZ_INIT = "SET time_zone='+00:00'"` 通过 `connect_args` 注入，alembic 同步引擎同样注入），因此**不再依赖** `docker-compose.yml` 里 mysql 服务的 `TZ: UTC`，本机开发也不需要改 MySQL 配置。若本端点仍报 `MySQLSessionNotUTC`，说明注入未生效（代码被改回或驱动不支持 `init_command`），属**代码问题**而非环境配置问题。
  若读不到时区（驱动 / 权限差异），只返回 `"utc": null` 而**不判失败**——附加校验不应把正常的连通性探测打成故障。
- ⚠️ **为什么把「库版本 ≠ 代码 head」也判成失败**：这是一种**只在部分接口上暴露**的静默失败 —— 应用能正常启动、`/health` 也返回 ok，但凡是 select 到新列（或查询新表）的接口都会 500（`Unknown column 'xxx' in 'field list'`），表现为「某几个页面加载失败」而不是「服务挂了」，排查时极易被误当成业务 bug。生产靠 compose 的 `migrate` 服务先跑 `alembic upgrade head`；本机开发则完全可能忘了跑。该判定**不会导致容器重启**（编排健康检查用的是 `GET /`）。
  读不到版本号（表不存在 / 权限不足）或读不到代码侧 head（脚本目录缺失）时只标记为「未知」（`null`）而**不判失败** —— 附加校验不应把一次正常的连通性探测打成故障。
- 建议接入 [Uptime Kuma](https://github.com/louislam/uptime-kuma)（可自托管）等探活服务，监控 `/api/v1/health/deep`，失败即告警。

**容器编排探针（healthcheck）一览**（与上面三级端点是两回事，供排障对照）：

| 服务 | 探针 | 说明 |
|------|------|------|
| `app` | `GET localhost:8000/` | 根路径探针（不是 `/health/deep`——依赖故障不应触发容器重启） |
| `mysql` | `mysqladmin ping` | 5s 间隔，start 期 30s 宽限 |
| `redis` | `redis-cli ping`（带密码） | |
| `prerender` | `GET /healthz` | 输出降级计数与队列深度 |
| `umami` | `GET /api/heartbeat` | |
| `postgres` | `pg_isready` | |
| `scheduler` / `migrate` | **无** | 有意为之：scheduler 存活靠 Redis 心跳 `ops:jobs:applied`（后台任务页可见），migrate 是一次性容器 |

#### 12.2.1 内置看门狗（零依赖，建议先开这个）

仓库自带 `scripts/watchdog.sh`，**不需要任何第三方服务**就能覆盖五类最容易被忽略的故障：

| 检查项 | 为什么它值得告警 |
|--------|------------------|
| 深度探活非 200 | 走 `/api/v1/health/deep`，覆盖 MySQL/Redis 连通、会话时区、schema 版本 |
| 容器崩溃循环（`restarting`） | 崩溃循环是最容易被忽略的故障（站点时好时坏，人却在看日志） |
| 容器 `Up` 但 `unhealthy` / 已退出（migrate 除外） | 「看起来在跑但其实坏了」比直接挂更难发现 |
| 磁盘使用率超阈值 | 磁盘满会让 MySQL 写不进、备份也写不下（默认 85%） |
| 最近备份超过 N 小时 / 备份目录缺失或不可写 | 「装了 cron 但没在跑」是最常见的**静默**失效（默认 48 小时） |

**开通三步**：

```bash
# 1) 在项目根 .env 填告警地址（企业微信机器人即可；飞书/钉钉/自建按企业微信 JSON 格式发；
#    Server酱 sctapi.ftqq.com 会自动改用 form 表单）
WATCHDOG_WEBHOOK='https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=<你的key>'

# 2) 安装定时任务（默认每 5 分钟）
./scripts/watchdog.sh --install-cron

# 3) 自检（分「配了吗 / 配在哪 / 装了吗」三问）并真的发一条测试告警
./scripts/watchdog.sh --doctor
./scripts/watchdog.sh --test-alert
```

> ⚠️ **三个必须知道的坑**（都属「看起来装好了、其实叫不醒人」）：
> 1. `WATCHDOG_WEBHOOK` 要写在 **`.env`** 里。自 2026-10-11 起 `watchdog.sh` 会自己读 `.env`；
>    在那之前它只认进程环境变量，而 **cron 不继承 shell 环境** —— 用
>    `WATCHDOG_WEBHOOK=xxx ./scripts/watchdog.sh --install-cron` 装过之后，
>    一旦重装时忘了带该变量，告警就会静默退回「只写日志」。
> 2. `WATCHDOG_HEALTH_HOST`（默认 `www.wdmao.cn`）**不能去掉**：nginx 对 80 端口的默认
>    server 块是「裸域 301 收敛到 www」，不带 Host 的探针会命中它拿到 301 并被判成故障
>    —— 换域名时需同步修改，否则站点会开箱即报假警。
> 3. 其余可调项（`WATCHDOG_HEALTH_URL` / `WATCHDOG_DISK_PERCENT` /
>    `WATCHDOG_BACKUP_MAX_AGE_HOURS` / `WATCHDOG_CRON` / `WATCHDOG_TIMEOUT`）见 `.env.example`。

**其余行为**（都可通过 `.env` 调整，见 `.env.example`）：

- **告警抑制**：同一标题的告警 30 分钟内只推第一条（`WATCHDOG_ALERT_SUPPRESS_SECONDS=1800`），
  窗口内的重复告警只写 `backups/watchdog.log`（`ALERT-SUPPRESSED`）——持续故障每 5 分钟推一条
  会把机器人刷屏，反而盖住「故障刚开始」那条。
- **日志轮转**：`watchdog.log` 超过 5MB（`WATCHDOG_LOG_MAX_BYTES`）自动改名为 `watchdog.log.1`
  （只保留 1 份历史），防止容器反复崩溃时把磁盘写满。
- 完整参数：`--uninstall-cron`（卸载）、`--status`（查 cron）、`--verbose`（正常时也打印明细）。

`./deploy.sh up` / `rebuild` 每次都会检查告警通道是否接通：**没配不会拦住发版，但会明确打印
「线上故障只会写本地日志，不会通知任何人」** —— 让这个缺口不可能被忽略。

> 需要多站点 / 可视化 / 状态页时再上 Uptime Kuma，两者不冲突。

### 12.3 日志聚合（⚠️ 未实现）

后端日志为 loguru 结构化 JSON 文件 sink（容器内 `/app/logs/app.log`，10MB 滚动、保留 14 天），**已挂载到宿主机**：`docker-compose.yml` 的 `app` 与 `scheduler` 两个服务都把 `./logs:/app/logs` 挂到同一个宿主目录（`deploy.sh` 会先建目录并 chown 到容器内 uid，否则只读挂载会让落盘静默失败）。

```bash
tail -f logs/app.log                                    # 结构化 JSON，宿主机直接看
docker compose exec app tail -n 200 /app/logs/app.log   # 或进容器看
docker compose logs --tail=100 app                      # 容器 stdout（含 docker json-file 驱动那份）
```

> 挂载本身是 P2-23 交付的，10.3 一直是这么记的）。仍然成立的缺口是**没有集中检索**，见下。

```bash
# 临时查看

# 长期方案（超出本说明书范围）：Loki + Promtail，或给 app/scheduler
# 挂载日志卷后由宿主机 Filebeat 采集
```

> （单文件 50M × 3）；compose 对 9 个服务另设了**服务级** json-file 上限
> （单文件 20M × 5，9 服务合计 ≤900MB）。前者管所有容器，后者覆盖本项目服务。

### 12.4 后台「系统状态」卡（只读运维视图）

后台「系统 → 状态」聚合页（`GET /api/v1/admin/system-status`）展示：深度探活结论、MySQL/Redis
连通性、schema 版本、**最近备份距今多久**、备份目录对容器是否可见、告警通道（webhook）是否已配置、
定时任务心跳与数据巡检结果等，逐项独立降级（单项故障不影响整卡），结果缓存 `SYSTEM_STATUS_CACHE_SECONDS`（默认 30s，调 0 = 每次实探）。

容器侧约定（改错会让卡片显示「不可见 / 过旧」）：

- `BACKUP_DIR` 在容器内**写死为 `/app/backups`**，不接受 `.env` 覆盖——compose 以
  `./backups:/app/backups:ro` 只读挂载宿主机备份目录，观测代码对备份没有写权限；
- 「备份过旧」阈值 `BACKUP_STALE_HOURS`（默认 48）与看门狗的 `WATCHDOG_BACKUP_MAX_AGE_HOURS`
  是同一口径，**两处别改得不一致**，否则会出现「看门狗说正常、后台说过期」；
- `WATCHDOG_WEBHOOK` 注入 app 仅为让「通道到底配没配」在后台可见——后端**不发送**告警，
  发送方是宿主机的 `scripts/watchdog.sh`。

## 13. CI 流水线（GitHub Actions）

> 对应的流水线文件：`.github/workflows/ci.yml`。
> 作用是把「发版时才知道坏没坏」提前到 push / PR 那一刻。

### 13.1 触发条件

| 事件 | 行为 |
|------|------|
| push 到 `master` / `main` | 跑全部四个 job |
| PR 指向 `master` / `main` | 同上（合并前的门禁） |
| 手动 `workflow_dispatch` | Actions 页面手动触发 |

同一分支连续 push 时，上一次未跑完的任务会被自动取消（工作流里的 `concurrency` 配置），避免排队堆积、白烧额度。

### 13.2 四个 job

| job | 运行时 | 内容 |
|-----|--------|------|
| `backend`（后端测试） | Python **3.11**（= `backend/Dockerfile`） | CI 配置自检 → `pytest tests/ -q`（**1474 用例**，离线）→ 文档链接校验 → 环境变量一致性校验 → `ruff check backend` → `check_nginx_conf.py`（nginx 配置自检）→ `check_compose_scalars.py`（compose 折叠标量自检）→ **`pack-deploy.sh` 部署包打包自检**（真跑一遍打包） |
| `migrations`（数据库迁移 · 真实 MySQL 8.0） | Python 3.11 + 服务容器 `mysql:8.0`（带 `--ngram_token_size=2`） | `alembic heads` **断言单 head**（多主直接失败）→ `upgrade head` → `current` → `downgrade base` → 再 `upgrade head`。 |
| `frontend`（前端 ${{matrix.app}}） | Node **22**（= `Dockerfile.nginx`） | matrix 依次跑 `frontend` 与 `admin-frontend`（`fail-fast: false`）：`npm ci`（有 lockfile 时严格）→ `npm run lint`（eslint）→ `tsc -b && vite build` → `npm test`（**两端都跑 vitest**）→ `npm audit --audit-level=high`（仅告警不阻断）。**用户端**额外跑错误监控脱敏回归（41 项）、预渲染内存降级回归（10 项）、小程序 tabBar 守卫 |
| `docker`（构建镜像） | — | **`backend` 与 `frontend` 两个 job 通过后**才跑（避免测试坏了还白烧 10 分钟构建额度）：`docker compose config -q` → `build app` → `build nginx` → `build prerender` |

> ⚠️ `migrations` job 需要 Docker-in-Docker 起 MySQL，是全流水线最慢的一环；**它红了先怀疑 MySQL 参数或权限差异，而不是代码**。

两条设计约束，改动前必须知道：

1. **CI 的语言版本与生产镜像强绑定。** `scripts/check_ci_config.py` 会校验 `PYTHON_VERSION` /
   `NODE_VERSION` 是否等于各 Dockerfile 的 `FROM` 版本，不一致直接失败。这是为了防住最坏的
   一种假绿：CI 在 Node 22 上全绿，而生产镜像还在 Node 20 上构建——本轮就是靠这条检查抓出
   `node:20` 已 EOL 却一直没人发现。
2. **单测必须离线可跑。** CI 里没有 MySQL / Redis，因此把 `DB_PORT` / `REDIS_PORT` 显式指向
   不可达端口。任何偷偷连真实服务的用例会立刻失败，而不是被本地开发环境掩盖。

### 13.3 在本地跑同样的检查

CI 里没有秘密，等价命令都能在本地执行（服务器上不需要这些，仅供排查时对照）：

```bash
# ① 后端：1474 个用例，全程离线（不需要 MySQL / Redis）
cd backend && DB_PORT=1 REDIS_PORT=1 python -m pytest tests/ -q
ruff check backend

# ② 迁移：在真实 MySQL 的临时库跑 upgrade → downgrade base → upgrade（需本机 MySQL；必须用 backend 的解释器）
backend/venv/Scripts/python.exe scripts/verify_migrations.py     # Windows
backend/venv/bin/python        scripts/verify_migrations.py     # Linux / macOS

# ③ 用户端：lint + 类型检查 + 生产构建 + 错误监控回归 41 项 + 预渲染降级 10 项 + 小程序 tabBar 守卫
cd frontend && npm run lint && npm run build && npm run test:monitoring
cd .. && node prerender/scripts/memory-guard-smoke.js && node scripts/check_tabbar.js

# ③' 管理端：lint + 类型检查 + 生产构建 + vitest（153 项）
cd admin-frontend && npm run lint && npm run build && npm test
cd ..

# ④ 五个静态自检（零依赖，标准库，任何 Python 3 都能跑）+ 打包自检
python scripts/check_ci_config.py        # CI 版本对齐 / 路径 / npm script / compose 服务
python scripts/check_docs_links.py       # 文档相对链接、锚点与重复章节编号
python scripts/check_env_consistency.py  # compose ↔ .env 模板 ↔ Settings 一致
python scripts/check_nginx_conf.py       # nginx 语法 / 双 Cache-Control
python scripts/check_compose_scalars.py  # compose 折叠标量内 # 注释
bash scripts/pack-deploy.sh /tmp/ci-pack.tar.gz   # 部署包打包自检

# ⑤ 镜像构建（等价于 docker job，耗时最长）
docker compose config -q && docker compose build app nginx prerender
```

### 13.4 常见失败与处理

| 现象 | 原因与处理 |
|------|-----------|
| `PYTHON_VERSION=3.11 与 … 的 FROM 版本 3.12 不一致` | 有人只改了 Dockerfile 或只改了 workflow。二者必须同时改；改完先跑一遍 `scripts/check_ci_config.py` |
| `npm ci` 报 lockfile 与 package.json 不同步 | 本地 `npm install` 后**把 lockfile 一并提交**。⚠️ 四个工程的 `package-lock.json` 都必须在库内，`.gitignore` **不要**再忽略它 |
| 用例在本地过、CI 上超时或连不上 | 几乎一定是新用例直连了真实 MySQL / Redis。改用 `async_client` 夹具 + `FakeRedis` |
| 镜像构建 job 很慢 | 后端镜像要 apt + pip 全量装依赖，前端镜像要跑两次 `npm ci` + `vite build`。`timeout-minutes` 已按 40 分钟设置；真觉得慢再加 BuildKit 缓存（`type=gha`），但那会让 CI 与 `docker-compose.yml` 的构建口径分叉，需谨慎 |
| 只改了文档却触发全量 CI | 当前**未做**路径过滤。文档改动仍会跑 `check_docs_links.py`（有价值）；不想等镜像构建的话，可在 Actions 页面单独取消该次运行 |

### 13.5 未做：CD（自动部署）

CI 只到「构建镜像」为止，**不会**推镜像仓库、**不会**远程触发 `./deploy.sh rebuild`。
服务器上更新代码仍走人工流程（见 10.1）。

要接上 CD，需要先定两件事：镜像仓库用哪个（GHCR / 腾讯云 TCR / 阿里云 ACR）、服务器怎么拉
（轮询 `docker compose pull`，还是 ssh 远程触发）。这属于独立决策，未随本轮完成——见。

## 14. 故障排查手册

### 14.1 通用排查思路

```bash
# 第一步：看容器状态
docker compose ps

# 第二步：看异常容器日志
docker compose logs --tail=100 <服务名>

# 第三步：进容器排查
docker compose exec <服务名> sh
```

### 14.2 场景：deploy.sh 提示密码为占位符

```
[error] .env 中 SECRET_KEY 未设置或仍为占位符
```

**原因**：`.env` 中对应字段仍是 `请替换为...` 占位符。

**解决**：编辑 `.env`，填入真实值后重新执行 `./deploy.sh up`。

### 14.3 场景：migrate 容器失败，app 不启动

**现象**：`docker compose ps` 中 `ai-cat-migrate` 显示 `Exited (1)`，`ai-cat-app` 未启动。

**排查：**

```bash
docker compose logs migrate
```

**常见原因：**

- MySQL 未就绪（少见有 healthcheck 保护）
- 迁移文件冲突（多人协作时）

**修复后重跑：**

```bash
docker compose up migrate              # 单独重跑迁移
docker compose up -d                   # 启动全部
```

### 14.4 场景：app 容器健康检查失败

**现象**：`ai-cat-app` 一直 `unhealthy`，`ai-cat-nginx` 不启动。

**排查：**

```bash
docker compose logs app
```

**常见原因：**

- `SECRET_KEY` 未设置（生产环境会拒绝启动）
- 数据库连接失败（检查 MySQL 是否 healthy）
- Redis 连接失败（检查 Redis 密码）

### 14.5 场景：前端访问 404 / 白屏

**排查步骤：**

```bash
# 1. 确认访问地址带末尾斜杠（后台必须）
#    正确: http://IP/admin/
#    错误: http://IP/admin

# 2. 确认 nginx 容器内静态文件存在
docker compose exec nginx ls /usr/share/nginx/html/
#   应看到: admin  assets  index.html ...
docker compose exec nginx ls /usr/share/nginx/html/admin/
#   应看到: assets  index.html

# 3. 看 nginx 日志
docker compose logs --tail=50 nginx
```

### 14.6 场景：API 返回 502 Bad Gateway

**原因**：nginx 无法连接后端 app。

**排查：**

```bash
# 1. app 是否运行
docker compose ps app

# 2. app 日志
docker compose logs --tail=50 app

# 3. app 重启循环则看启动报错
```

### 14.7 场景：文件上传失败

**排查：**

```bash
# 1. 检查 .env 中 COS 配置
grep COS .env

# 2. 看后端日志中的 COS 报错
docker compose logs app | grep -i cos

# 3. 文件是否超 20MB（设计限制）
#    超出会返回错误，提示用户用网盘
```

### 14.8 场景：AI 对话无响应

**排查：**

```bash
# 1. 确认 DEEPSEEK_API_KEY 已配置
grep DEEPSEEK .env

# 2. 看后端日志
docker compose logs app | grep -i deepseek

# 3. 服务器能否访问 DeepSeek
docker compose exec app curl -s https://api.deepseek.com/v1 -o /dev/null -w "%{http_code}"
```

### 14.9 场景：管理后台 401 后跳转错误

**现象**：登录态失效后跳到 `/login` 而非 `/admin/login`。

**排查：** 确认 `admin-frontend/src/api/client.ts` 中跳转地址为 `/admin/login`（部署方案已调整，若从旧代码升级需检查）。

### 14.10 场景：磁盘被日志撑满

**解决：**

```bash
# 查看磁盘
df -h

# 清理容器日志（已配置 log-opts 限制，但历史日志需手动清）
docker compose down
sudo sh -c 'truncate -s 0 /var/lib/docker/containers/*/*-json.log'
docker compose up -d
```

> 已在 3.5 节配置 `log-opts` 限制单文件 50M、最多 3 个（宿主机全局）；compose 服务级另有
> 单文件 20M × 5 的上限（9 服务合计 ≤900MB），两级配置详见 12.3。

### 14.11 场景：mysql 起不来，报 `Too many arguments (first extra is '#')`

**现象**：`ai-cat-mysql` 反复重启或 abort，`app`/`nginx` 因 depends_on 全部未启动，整站 502；
日志首行含 `[MY-010147] Too many arguments (first extra is '#')`。

**原因**：`docker-compose.yml` 里 mysql 的 `command: >` 是 YAML **折叠标量**——其下缩进更深的行
全部是字面文本，里面的 `#` **不是注释**，会被原样拼进 mysqld 命令行（2026-10-20 线上事故；
`docker compose config` 不报错，肉眼极难发现）。

**解决**：把说明文字移到 `command: >` 块**外面**（同级或更浅缩进）。CI 的
`python scripts/check_compose_scalars.py` 会拦截此类改动；本地改完 compose 后先跑一遍它。

### 14.12 场景：静态资源响应头出现两条 Cache-Control

**现象**：`curl -I` 看到两条 `Cache-Control`；Safari 等只认首条 → 发版后部分浏览器仍拿旧资源。

**原因**：nginx 里 `expires` 与 `add_header Cache-Control` 并写——`expires` 自己会产出一条
Cache-Control，而 `add_header` 是追加不是替换（nginx.conf 两处事故注释）。

**解决**：合并成一条 `add_header Cache-Control "public, max-age=..., immutable" always;`。
CI 的 `python scripts/check_nginx_conf.py` 会拦截；改完 `docker compose restart nginx` 即可（挂载文件）。

### 14.13 场景：IndexNow / 百度推送「装了但从来没推过」

**现象**：站点正常，但收录推送无任何产出，日志里推送任务静默跳过。

**排查**：

```bash
grep -E 'INDEXNOW_KEY|BAIDU_PUSH_TOKEN' .env
docker compose exec scheduler printenv | grep -E 'INDEXNOW|BAIDU'
```

**原因（历史事故 P2-24）**：这两个变量必须**同时注入 app 与 scheduler 两个服务**——推送任务跑在
scheduler，此前只有 app 注入了 `INDEXNOW_KEY`，定时任务在生产从未真正推送。当前 compose 已补齐；
新增 SEO 类变量时务必逐服务检查注入（模板：compose 的 app 与 scheduler 两个 environment 块）。

### 15.1 必做项

- [ ] `.env` 中三处密码均为强密码（非占位符）
  > ⚠️ 若密码为空、仍为 `root` 或模板占位符，生产环境会**拒绝启动**（fail-fast，见 15.5）
- [ ] `SECRET_KEY` 已用 `openssl rand -hex 32` 生成
- [ ] `.env` 文件权限 `chmod 600 .env`
- [ ] 服务器仅放行 80 端口（3306/6379/8000 不对公网开放，本方案已默认内部网络）
- [ ] 管理员默认密码已修改
- [ ] `.env` 未提交到 git
- [ ] **Umami 统计后台已改掉出厂口令 `umami/umami`**（见 15.4——`deploy.sh` 不生成、不打印任何 Umami 口令，撤掉 Basic Auth 后唯一防线就是你自己改的这个口令）

### 15.2 建议项

- [ ] 配置服务器 SSH 密钥登录，禁用密码登录
- [ ] 启用 `ufw` 或云防火墙，仅放行 22/80（443）
- [ ] 定时备份 MySQL（见 11.3）
- [ ] 配置 fail2ban 防暴力破解 SSH
- [ ] 定期 `docker compose pull && docker compose up -d` 更新基础镜像
- [ ] 后续配域名 + HTTPS（见第 16 节）

### 15.3 已内置的安全措施

- 生产环境关闭 `/docs` 与 `/redoc`（`APP_ENV=production` 时）
- 后端上传文件扩展名白名单（仅图片）
- 限流中间件（游客 120/分钟，登录用户 300/分钟）
- nginx 安全头（`X-Content-Type-Options`、`X-Frame-Options`、`Referrer-Policy`）
- nginx 隐藏版本号（`server_tokens off`）
- 上传体积限制（nginx 25M，后端 20M）
- **容器权限加固**：自研镜像非 root 运行（appuser）；compose 对 app/scheduler/migrate/prerender
  施加 `no-new-privileges` + `cap_drop: ALL`，nginx 施加 `no-new-privileges`
- **Redis 内存上限**：`maxmemory 512mb` + **`noeviction`**（而非 `allkeys-lru` —— 本实例混放
  token 黑名单 / 版本号 / refresh_token，LRU 会在内存紧张时**静默复活已登出的 token**）
- **Umami 子域靠应用自身口令**（Basic Auth 已撤，见 15.4）

### 15.4 Umami 统计后台的访问控制

Umami 出厂默认口令 `umami/umami` 是**公开知识**，而 `tj.wdmao.cn` 暴露在公网 ——
不加固等于把统计后台交出去（可接管数据、注入恶意埋点脚本反向污染前台页面）。

**当前唯一的防线是 Umami 自己的管理员口令，所以部署后必须立刻改掉出厂值。**

> **⚠️ 不要再给这个子域加 nginx Basic Auth —— 它对 Umami v3 根本不工作。**
> v3 改用 **Bearer token** 认证（登录接口返回 `{token}` 且不下发 cookie，之后每个 API
> 请求由前端自带 `Authorization: Bearer ...`）。一个请求只能有一个 `Authorization` 头，
> 它被 Bearer 占了，浏览器就没法再附上 Basic 凭据，于是 `/api/*` 全部被源站 401 拦下。
> 2026-10-14 实测（凭据完全正确）：浏览器提交登录 → `POST /api/auth/login` 返回 nginx 的
> HTML 401 页 → 前端 `JSON.parse` 报 `Unexpected token '<'`，登录页永远停在 `/login`；
> 而同一份凭据用 curl 发（没人占这个头）能拿到 200 + token。
> 第二轮审查 P0-3 加的那层当时能进，是因为跑的还是 v2 的 cookie 认证。
>
> 
> 顺带消掉了「挂载源缺失被 Docker 建成同名目录 → nginx 起不来 → 整站 502」这个坑。

加固手段按优先级：

| 手段 | 做法 | 说明 |
| --- | --- | --- |
| **必做** | 登录 `https://tj.wdmao.cn` → Settings → Users → 改掉 `admin` 的口令 | 用密码管理器生成 20 位以上随机串；这是撤掉 Basic Auth 后的唯一防线 |
| 推荐 | EdgeOne 给 `tj.wdmao.cn` 加访问控制（IP 白名单 / 边缘 ACL） | 在边缘层做，不占用 `Authorization` 头，因此与 v3 的 Bearer 认证不冲突 |
| 可选 | EdgeOne 对 `/api/auth/login` 限速 | 削弱在线爆破口令的能力 |

```bash
# 改完口令后自检：出厂值必须不再可用（期望 401），新口令期望 200
curl -s -o /dev/null -w '%{http_code}\n' -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":"umami"}' https://tj.wdmao.cn/api/auth/login
```

> **⚠️ 埋点与上报路径必须保持匿名**：`/script.js`、`/api/send`（v2 为 `/api/collect`）
> 是前台页面浏览器**匿名**调用的，任何访问控制罩住它们都会让统计**静默失效** ——
> 页面照常打开、数据一条不上来、且没有任何报错。`nginx.conf` 里这三个 location 单独成块
> 还为了 `client_max_body_size 64k`（未鉴权的匿名 POST 不应吃到 http 级的 25M 上限，
> 第四轮审查 P1-68），改动时请保持这两点。

### 15.5 生产环境的启动期校验（fail-fast）

后端在 `APP_ENV != development` 时，会对几项配置做**启动即失败**的校验 ——
目的是把「部署漏配」挡在上线之前，而不是带着弱凭据跑几个月才发现：

| 校验项 | 触发条件 | 为什么 |
|--------|---------|--------|
| `SECRET_KEY` | 为空默认值 / 长度 < 32 | 它是 JWT 签名与凭据加密的根密钥 |
| `CORS_ORIGINS` | 配置为 `*` | 与 `allow_credentials=True` 不兼容，跨域带 cookie 请求会静默失败 |
| `DB_PASSWORD` | 为空或等于 `root` | 数据库弱口令（`check_env_consistency.py` 会校验，弱口令直接失败） |
| `REDIS_PASSWORD` | 为空 | Redis 存有**安全状态**：令牌黑名单 / 令牌版本号 / refresh_token / RBAC 权限缓存。无鉴权时，任何能进入容器网络的进程都可读改它们 —— **改权限缓存即可提权** |

> 遇到启动报错时，按错误消息里的提示修改 `.env` 后重启即可（错误消息已写明改哪个变量）。
> 这几项在**本地开发**（`APP_ENV=development`）**不会触发**，不影响 `scripts/start-backend.bat` 等本地流程。

## 16. 域名与 HTTPS 配置

### 16.1 方案选择

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| Caddy 自动签发 | 配置极简，自动续期 | 需新增 Caddy 容器 |
| Nginx + Certbot | 无需新增组件 | 需手动续期或配定时任务 |
| 云厂商 SSL | 省心 | 可能收费 |

### 16.2 方案 A：Caddy 自动 HTTPS（推荐）

新建 `Caddyfile`：

```
yourdomain.com {
    reverse_proxy ai-cat-nginx:80
}
```

在 `docker-compose.yml` 顶部增加 Caddy 服务：

```yaml
  caddy:
    image: caddy:2-alpine
    container_name: ai-cat-caddy
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
      - caddy_data:/data
      - caddy_config:/config
    depends_on:
      - nginx
    restart: unless-stopped
    networks:
      - ai-cat-net
```

同时把 nginx 服务的端口映射改为仅内部：

```yaml
  nginx:
    # 删除 ports 映射, 仅通过 caddy 反代
    # ports:
    #   - "80:80"
```

启动：

```bash
docker compose up -d caddy
```

Caddy 会自动签发 Let's Encrypt 证书并续期。

### 16.3 方案 B：Nginx + Certbot

```bash
# 1. 域名解析到服务器 IP
# 2. 安装 certbot
sudo apt install -y certbot

# 3. 停掉 nginx 释放 80 端口
docker compose stop nginx

# 4. 签发证书
sudo certbot certonly --standalone -d yourdomain.com

# 5. 证书路径: /etc/letsencrypt/live/yourdomain.com/
```

修改 `docker-compose.yml` 的 nginx 服务：

```yaml
  nginx:
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./nginx.conf:/etc/nginx/nginx.conf:ro
      - /etc/letsencrypt:/etc/letsencrypt:ro
```

在 `nginx.conf` 增加 443 server 块并 80→443 跳转：

```nginx
server {
    listen 80;
    server_name yourdomain.com;
    return 301 https://$host$request_uri;
}
server {
    listen 443 ssl;
    server_name yourdomain.com;
    ssl_certificate     /etc/letsencrypt/live/yourdomain.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/yourdomain.com/privkey.pem;
    # ... 其余 location 配置同原 80 端口
}
```

续期（crontab）：

```bash
0 3 1 * * certbot renew --quiet && docker compose restart nginx
```

### 16.4 启用 HTTPS 后的额外配置

`.env` 中补充（可选，用于 CORS）：

```env
CORS_ORIGINS=https://yourdomain.com
```

## 17. 性能调优建议

### 17.1 后端 Worker 数

`backend/Dockerfile` 中 `-w 2` 表示 2 个 gunicorn worker。CPU 核数多时可调大：

```dockerfile
CMD ["gunicorn", "-k", "uvicorn.workers.UvicornWorker", "-w", "4", "-b", "0.0.0.0:8000", "app.main:app"]
```

> 经验公式：worker 数 = (2 × CPU 核数) + 1

### 17.2 MySQL 调优

在 `docker-compose.yml` 的 mysql 服务挂载自定义配置：

```yaml
  mysql:
    command: >
      --character-set-server=utf8mb4
      --collation-server=utf8mb4_unicode_ci
      --innodb-buffer-pool-size=1G
      --max-connections=200
```

> `innodb-buffer-pool-size` 建议设为可用内存的 50–70%。

### 17.3 前端缓存

已配置：JS/CSS 等静态资源 30 天长缓存（hash 文件名），入口 HTML 不缓存。发版后用户刷新即可拿到新版本。

### 17.4 Gzip

已在 nginx.conf 启用，压缩级别 6，覆盖常见文本类型。
