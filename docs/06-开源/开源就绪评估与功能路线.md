# 后台管理端 开源就绪评估与功能路线

> 评估日期：2026-10-29　评估对象：`ai-cat`（backend + admin-frontend，含用户端与小程序依赖关系）
> 视角：架构 / 产品 / 开源维护者三方交叉。结论只针对「对外开源」这件事，不评价线上运营。

---

## 一、结论速览

| 维度 | 现状 | 判断 |
|------|------|------|
| 工程质量 | 253 个后端文件、145 个测试文件（935 用例）、79 个 Alembic 迁移、CI 四 job、3 个零依赖自检脚本 | **8.5 / 10**，明显高于同类开源后台 |
| 后台产品完备度 | 32 个页面，覆盖用户/内容/审核/支付/积分/RBAC/审计/定时任务/设置中心 | **7.5 / 10**，缺的是「效率型功能」而非「能力型功能」 |
| 可移植性 | 104 个环境变量、腾讯云 COS、微信支付/小程序、SMTP、多个三方图片源 | **4 / 10**，别人跑不起来 = 开源即沉默 |
| 开源就绪度 | 无 LICENSE、无 CONTRIBUTING、无英文 README、仓库内存在备份 SQL 与日志、git 历史 335 次提交未清洗 | **2 / 10**，这是当前最大短板 |

**三句话结论：**

1. 现在直接开源，读者会做两件事：先看许可证（没有 → 关掉），再看怎么跑（104 个 env → 关掉）。
2. 功能上不需要再造轮子，但必须补 **导出、统一回收站、安装向导、存储/支付抽象** 这四块，它们决定"能不能被别人当自己的项目用"。
3. 真正的护城河不是 CRUD，而是你已经做对的两件事：**RBAC 权限目录与菜单同源**、**审计留痕**。这两点要在 README 里当卖点讲，而不是埋在 `rbac_catalog.py` 注释里。

## 二、先定范围（这一步决定后面所有工作量）

| 方案 | 内容 | 受众 | 工作量 | 风险 |
|------|------|------|--------|------|
| **A. 整套平台开源**（推荐） | admin + backend + frontend + 部署脚本 | 想自建「AI 内容站」的人 | 中 | 用户端也开源，商业差异化要靠内容与运营，不靠代码 |
| **B. 只开源「后台管理端」** | admin-frontend + backend 中 admin 相关 API | 想找通用后台脚手架的人 | **大** | admin 与 `tutorial/resource/node/tool/plugin` 五种内容模型强耦合，不做「内容类型注册表」抽离，别人没法用 |
| **C. 开源「通用后台骨架」** | 剥离业务，只留 RBAC + 审计 + 设置 + 用户 | 同上 | **最大** | 等于重写，且失去现有全部亮点 |

> **已决策（2026-10-29）：走 B —— 只开源后台管理端。**
> B 的执行细节、模块切割清单与里程碑见 [仅开源后台管理端-切割方案](仅开源后台管理端-切割方案.md)。
> 该方案采取「代码全保留 + 模块注册表开关」的方式规避 C1（内容类型抽离）的前置成本，
> 因此不必先做重构成 `modules/` 目录，但**必须新增 `module_registry.py` 并让
> `router.py` / `admin_menu.py` / `rbac_catalog.py` 三处从它派生**。

## 四、功能缺口（按对"开源可用性"的贡献排序）

> 本节是 2026-10-29 的评估快照，用来解释优先级；已完成项（导出、会话管理、数据权限、待办中心等）
> 以 [README 路线图](../../README.md#路线图) 为准，不在此逐行回改。

### A. 可移植性 —— 别人能不能跑起来（P0）

| # | 缺口 | 现状证据 | 建议做法 |
|---|------|---------|---------|
| A1 | **存储未抽象** | 图片/附件/头像全部走腾讯云 COS，`cos_service.py` 单一实现 | 抽 `StorageProvider` 接口（put/get/delete/sign_url），落三个实现：`local`（默认，挂卷）、`s3`（兼容 MinIO/R2/OSS）、`cos`。**没有 local 实现，开源用户第一步就卡死** |
| A2 | **三方能力无 Mock** | 微信支付/小程序、支付宝、短信、邮件、DeepSeek/OpenAI/Qwen 均为直连 | 每个能力加 `NullProvider`/`MockProvider`，env 不配时降级为「功能关闭」而非 500。已有的 `WECHAT_MINI_*` 空值返回 503 是正确范式，推广到支付/短信 |
| A3 | **一键跑不起来** | `docker-compose.yml` 29 KB，含 app/nginx/prerender/mysql/redis/umami/watchdog 七服务 | 加 `compose profile`：`minimal`（app+mysql+redis+nginx，无预渲染无 umami）、`full`。README 首屏只给 minimal 一条命令 |
| A4 | **无安装向导** | 靠 `alembic upgrade` + `seed_data.py` + 手填 env | 首次启动检测「无管理员账号」→ 前端进 `/admin/setup`：创建管理员、选存储方式、测邮件、生成 `SECRET_KEY`。这是开源项目转化率最高的一步 |
| A5 | **env 过多** | 104 个键 | 分层：`必需 6 项`（DB/Redis/SECRET_KEY/ADMIN_PASSWORD/SITE_BASE_URL/存储）→ 其余全部可运行时在后台配置（`SystemSetting` 已支持，把 AI/支付/邮件/图片源全部迁到后台可视化配置，env 只做覆盖兜底） |
| A6 | **数据库只支持 MySQL** | SQLAlchemy 异步 + MySQL 专属特性（全文索引 `ngram`） | 二选一：明确声明「仅 MySQL 8」并在 README 写清；或提供 Postgres 兼容路径（全文检索降级为 `ILIKE`）。**推荐明确声明**，成本最低 |

### B. 后台产品力 —— 别人愿不愿意用（P1）

| # | 缺口 | 现状证据 | 价值 |
|---|------|---------|------|
| B1 | **无数据导出** | 全端 `grep` 无 CSV/XLSX 导出，只有 `admin_ai_writing` 的流式响应 | 用户/订单/积分/审核记录导出，是后台第一刚需。做一个通用 `export?format=csv` 混入 + 前端「导出当前筛选结果」按钮 |
| B2 | **回收站不统一** | `restore` 分散在 26 处（资源/评论/用户…），无统一入口页面 | 加「回收站」页面：按模块聚合软删除项、批量恢复、保留期倒计时、到期自动清理任务 |
| B3 | **无后台工作台/待办** | `Dashboard` 是指标看板（趋势/漏斗/归因），无「待我处理」 | 顶部铃铛 + 待办聚合：待审实名 N、待处理举报 N、待回反馈 N、失败定时任务 N、额度将尽提示。管理员的真实入口是待办，不是图表 |
| B4 | **配置中心缺"生效感"** | 14 组设置，有未保存脏标记，但无「连接测试 / 生效范围 / 是否需要重启」 | 每类配置加「测试连接」（`ai_model_probe_service` 已有范式）、标注「保存即生效 / 需重启 / 仅新请求生效」、配置变更写审计 |
| B5 | **无会话与设备管理** | 无强制下线、无在线管理员列表、无 token 吊销 | 改成密码后其他设备未失效是常见安全事故。加 `GET /admin/sessions` + 吊销；**管理员强制 2FA**（`totp_service` 已实现，只是用户侧可选，管理端应可强制） |
| B6 | **审计日志无 diff** | `admin_audit_log` 有记录，无「改前/改后」 | 高危操作（改价、改权限、删用户）记录字段级 diff，前端抽屉对比展示 |
| B7 | **仅 PC + 仅亮色** | `Sider` 固定 `100vh`、`themeConfig` 单套 token | 审核/客服场景大量在手机上处理。至少让「评论/举报/反馈」三页响应式；暗色跟随系统（AntD `algorithm` 切换，成本很低） |
| B8 | **无全局搜索** | 侧栏导航 + 页内搜索 | `Ctrl+K` 命令面板：跳页面、搜用户、搜内容、执行动作。大后台的体感分水岭 |
| B9 | **导入能力弱** | 有 `ThirdPartyImport.tsx`（单点） | CSV/Markdown 批量导入 + 字段映射预览，是「从别的 CMS 迁移过来」的唯一通道 |
| B10 | **权限只到按钮级** | `rbac_catalog` 全为 `menu`/`button` 两级 | 缺**数据范围**（本人 / 本部门 / 全部）。`Departments` 已存在，但没有落到数据过滤上。多人协作时这是刚需，单人站长不需要 —— 按目标受众取舍 |

### C. 平台化与生态 —— 能不能长大（P2 / 视范围而定）

| # | 缺口 | 说明 |
|---|------|------|
| C1 | **内容类型未抽象** | `tutorial/resource/node/tool/plugin` 五种类型各有一套 CRUD、各一套权限码、各一套前端 List/Edit 页。抽「内容类型注册表」（字段 schema + 权限前缀 + 列表列配置），五种类型降级为配置。**这是"只开源后台"路线的前置条件**，也是让外部贡献者加自己的内容类型不用改核心的关键 |
| C2 | **插件机制名不副实** | `admin_plugins` 是「扩展推荐」业务模块，不是代码插件体系 |
| C3 | **无对外开放 API** | 无个人访问令牌（PAT）、无 Webhook 事件订阅。二次开发者只能改源码 |
| C4 | **零国际化** | ⚠️ 部分完成（2026-10-30）：后端菜单 / 权限名中英，前端外壳 / 登录 / 命令面板 / 列表通用组件可切换并持久化；教程、用户、运营等业务页面文案仍为中文，待逐页迁移 |

### D. 自托管运维 —— 开源自部署的第一道坎（P1）

| # | 缺口 | 说明 |
|---|------|------|
| D1 | **无系统体检页** | `SystemStatusPanel` + `/health/deep` 已有，但只对「本站」；需要「安装体检」：DB/Redis/存储/邮件/AI Key/定时任务 六项连通性一键测 + 修复指引 |
| D2 | **备份恢复无 UI** | `deploy.sh`/watchdog 有备份脚本，无后台入口。自托管用户最怕「升级炸了」 |
| D3 | **无版本与升级提示** | 需要 `GET /admin/version`（代码版本 / 迁移 head / 待执行迁移数 / 最新 release）+ 升级前自动备份提醒 |
| D4 | **无演示模式** | 公开 demo 必须有只读账号 + 定时重置，否则第一天就被灌垃圾数据 |

## 五、架构建议（三个抽象 + 一个注册表）

```
                    ┌──────────────── Admin Frontend (Vite/React) ────────────────┐
                    │  菜单 ← /admin/menus   权限 ← RBAC catalog（已同源，保持）    │
                    └──────────────────────────┬──────────────────────────────────┘
                                               │ OpenAPI 生成类型（替换手写 types/）
┌──────────────────────────────────────────────▼──────────────────────────────────┐
│ FastAPI                                                                          │
│  ├─ api/admin_*         （已有 30 个模块，保持一模块一文件）                      │
│  ├─ ContentTypeRegistry （C1：schema + 权限前缀 + 列配置 + 钩子）                 │
│  ├─ providers/                                                                   │
│  │    ├─ storage:   local | s3 | cos        （A1）                               │
│  │    ├─ payment:   mock | wechat | alipay  （A2）                               │
│  │    ├─ sms/mail:  mock | smtp | aliyun    （A2）                               │
│  │    └─ notify:    webhook | mail          （B3/C3）                            │
│  └─ settings          env 做兜底，DB 做默认（A5）                                 │
└──────────────────────────────────────────────────────────────────────────────────┘
```

三条原则，建议写进 `CONTRIBUTING.md`：

1. **同源原则**（你已经做对了，要固化）：菜单、权限码、路由守卫、后端依赖注入，四处由一个目录派生。新模块只加一处。
2. **失败降级原则**：任何三方能力未配置时，系统必须能跑，影响面收敛到"该功能不可用 + 后台体检页标红"，而不是启动失败或 500。
3. **可观测优先**：新增写操作必须同时产出审计记录（`test_admin_audit_coverage.py` 已经在守这件事，把它写进文档当作卖点）。
