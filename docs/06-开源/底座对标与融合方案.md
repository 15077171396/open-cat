# 底座对标与融合方案（Python + React）

> 目标：把 `ai-cat` 的后台底座在**性能 / 安全 / 易扩展 / 易维护 / 组件封装 / 代码封装**六个维度上拉到「开源后经得起挑刺」的水平。
> 对标：go-admin、RuoYi、FastapiAdmin、zq-platform、JeecgBoot。
> 技术栈基线：后端 FastAPI + SQLAlchemy 2 异步 + MySQL/Redis；前端 React 18 + AntD 6 + Vite。
> 日期：2026-10-29。配套文档：[仅开源后台管理端-切割方案](仅开源后台管理端-切割方案.md)

---

## 一、先给结论：你缺的不是安全，是「可证明性」和「抽象层」

我把现有代码里与这六个维度相关的实现逐项查了一遍，结果和"感觉不太行"的直觉并不一致：

| 维度 | 现状证据 | 实际水平 |
|------|---------|---------|
| 密码学与凭据 | `core/security.py` bcrypt + `core/executors.py` 把 bcrypt 丢线程池（防阻塞事件循环）+ 登录对 dummy hash 做真实校验（防时序侧信道）+ `core/crypto.py` **第三方密钥 Fernet 加密落库**（PBKDF2 派生、密文版本化 `enc:v2:`、掩码哨兵防回写） | **明显高于对标项目**。RuoYi/FastapiAdmin/JeecgBoot 的第三方密钥基本是明文存库或存文件 |
| 边界防护 | `RateLimitMiddleware`（Redis 固定窗口，敏感端点 **fail-closed**）、`SecurityHeadersMiddleware`、`RequestIdMiddleware`、CORS 白名单 | 中上。缺"运营侧"能力（见 §四.2） |
| 数据出口 | `utils/sanitize.py` + `upload_validation.py` | 中上。需核查是否覆盖全部富文本出口 |
| 并发优化 | 全仓 `selectinload/joinedload` 仅 **24 处** | **弱**。列表接口 N+1 没有被系统性治理 |
| 抽象封装 | 无通用 CRUD 基类、无代码生成、无声明式导入导出；50 个页面里只有 13 个用 `useCrudList`，24 个页面直接手写 `<Table>`；`AiModels/index.tsx` 1231 行、`Tutorials/Edit.tsx` 1016 行 | **弱**。这是"感觉底座不行"的真实来源 |
| 可测量性 | 无性能基准、无慢查询阈值告警、无覆盖率门槛 | **弱**。没有数字，就无法反驳"性能不行"的判断 |

**三句话：**

1. 密码学侧你已经领先，**不要**去抄 RuoYi 的 Shiro + 明文参数表那套；
2. 你真正落后的是 **RuoYi 的 `@DataScope`、Jeecg 的代码生成器、zq 的 `base_service`、FastapiAdmin 的 `ENABLED_MODULES`** 这四件「抽象层」的东西；
3. "性能不行"目前是**主观判断**，第一步不是优化，是**建立基线**——没有 P95 数字，任何优化都无法验收。

## 二、五个项目的精华与糟粕

### 2.1 go-admin（Gin + Casbin + Vue）

**精华（值得拿）**

| 机制 | 说明 | 对我们的用法 |
|------|------|-------------|
| **多命令 CLI** | `go-admin migrate -c config/settings.yml` / `go-admin server`，迁移与服务分离，配置由 viper 映射到结构体 | 我们有 Alembic 但没有统一 CLI 入口。可加 `python -m app.cli migrate/seed/doctor` |
| **中间件链设计** | 认证、跨域、访问日志、**tracking ID** 各为独立中间件，顺序显式 | 已有 RequestId，可对齐「中间件顺序表」写进文档 |
| **Casbin 策略化鉴权** | 权限判定走策略表而非代码分支，可运行时改 | 我们的 RBAC 是代码 + DB 混合，已够用；**不迁移**，但可借「策略可热更新」的思路 |
| **配置即文档** | `config/settings.yml` 全量注释 | 我们的 `.env.example` 18KB 已是同类资产，可提炼为「配置项说明表」 |

**糟粕（别抄）**

- README 自己写着 `TODO: unit test` —— **一个零测试的脚手架**。抄架构可以，抄工程纪律会毁掉你现有的 935 个用例；
- 代码生成器先生成 GORM 结构体再由反射推导，字段注释一丢就废；产出的代码无法表达业务约束（你的 `access_mode`、`points_price` 归一化规则它就生成不出来）；
- GORM 隐式 Preload 容易掩盖 N+1，与你的显式 `selectinload` 取向相反。

**适用性评级：★★★☆☆**（CLI 与中间件秩序可抄，其余不适用）

### 2.2 RuoYi（SpringBoot + Shiro + MyBatis）

**精华（值得拿，且是我们最缺的）**

| 机制 | 说明 | 对我们的用法 |
|------|------|-------------|
| **`@DataScope` 数据权限切面** | 按角色配置「全部 / 本部门 / 本部门及以下 / 仅本人」，AOP 自动往 SQL 追加 `dept_id in (...)` | 我们有 `Departments` 表却**没有数据过滤**。这是"多人协作运营"的刚需，用 FastAPI 依赖 + SQLAlchemy 查询重写实现等价物 |
| **`@RepeatSubmit` 防重复提交** | 注解 + Redis 键（用户+URL+参数）短 TTL 拦截 | 我们有前端防抖，但**后端无幂等**。改成装饰器 `@idempotent(key, ttl)` |
| **`@RateLimiter` 端点级限流** | 方法级注解，与全局中间件互补 | 我们只有全局 IP 维度。补「按用户/按端点」维度 |
| **字典管理** | 一套 `sys_dict_type/data` 支撑全站枚举，前端 `<dict-tag>` 组件统一渲染 | 我们枚举散落在 `Literal[...]` 与前端常量里。**强烈建议补**，它同时解决前端组件封装 |
| **`@Excel` 声明式导入导出** | 字段加注解即获得 Excel 列映射 | 我们的导出是零。用 `openpyxl` + dataclass 声明式字段实现同类能力 |
| **在线用户 / 缓存监控 / 连接池监视** | 运维可观测三件套，直接在后台看 | 我们有 `SystemStatusPanel`，可扩展为「在线会话 + 缓存键浏览 + 连接池水位」 |
| **定时任务可视化** | 在线增删改 + 执行日志 | 我们已有 `ScheduledJobs`（只读），补「手动触发 + 执行历史」即可 |

**糟粕（别抄）**

- 技术栈老化：Shiro + Hplus 模板，前端仍是服务端渲染风格，与 React 无关；
- 代码生成器产出的是**字符串模板拼接**，产物难维护，且默认无测试；
- 权限码与菜单强绑 `sys_menu.perms`，导致"按钮权限"必须挂在菜单树下，扁平授权做不了（我们的 `rbac_catalog` 反而更干净）；
- 生态分支极多（RuoYi / RuoYi-Vue / RuoYi-Cloud / RuoYi-Plus），**上游碎片化**是选型风险。

**适用性评级：★★★★★**（数据权限、幂等、字典、导出四件直接可搬）

### 2.3 FastapiAdmin（FastAPI + Vue3，与我们同栈）

**精华（同栈，几乎可以照着改）**

| 机制 | 说明 |
|------|------|
| **`ENABLED_MODULES` 模块开关** | `setting.py` 里一个列表决定哪些模块加载；移除列表项即卸载接口、WebSocket 端点与初始化逻辑，**不改代码不删菜单**。这与我们[切割方案](仅开源后台管理端-切割方案.md)的 `module_registry` 完全同构，是**最值得直接借鉴的一条** |
| **五种存储协议** | SFTP / S3 / OSS / COS / OBS 统一抽象 | 我们只有 COS。抄它的接口形状（`put/get/delete/sign_url/presign_upload`） |
| **菜单 / 按钮 / 数据三级权限** | 比我们多一级数据权限 | 与 RuoYi `@DataScope` 互为印证 |
| **拼图验证码** | 登录 + 滑块拼图，Redis 存态 | 我们无验证码（靠限流 + 锁定）。可加，作为开源项目的"安全感"门面 |
| **在线用户 / 服务器监控 / 缓存监控** | 后台直接可见 |
| **MySQL / PostgreSQL / SQLite 三方言** | 方言适配层 | 我们是 MySQL 专属（`ngram` 全文索引）。**建议明确声明只支持 MySQL 8**，别做三方言（见 §五） |
| **monorepo + uv** | `backend/` `frontend/web` `frontend/app` `docker/` 同级 | 与我们计划的两目录结构一致，可参考其 `deploy.sh` 一键脚本 |

**糟粕（别抄）**

- 自述**单实例设计**：WebSocket 与调度器基于进程内存，水平扩展要自己接 Pub/Sub —— 我们的 APScheduler 也有同样问题，但它把限制写进 README 是加分项，抄这个"诚实声明"；
- 功能堆得过满（内部 IM、AI 对话、代码生成、工作流），**开源项目的失焦风险**；我们应反过来做减法；
- 移动端用 UniApp 独立一套，等于维护第二套前端 —— 我们已有原生小程序，不要再叠一层。

**适用性评级：★★★★★**（同栈，模块开关 + 存储抽象直接落地）

### 2.4 zq-platform（FastAPI + Vue3 + Vben）

**精华（架构层次最值得我们学）**

| 机制 | 说明 |
|------|------|
| **垂直切片目录 `core/<domain>/`** | `core/user/`、`core/role/`、`core/menu/`、`core/login_log/` 各自成包，而非 `api/ models/ services/` 三层横切 | 我们正是横切分层，一个"支付"散在 6 处。**渐进式迁移**：新模块用切片，老模块不动 |
| **`base_model` / `base_schema` / `base_service`** | 三层基类把 CRUD、分页、软删、时间戳、审计字段全部收敛 | 我们每个模块手写 `list/get/create/update/delete`。这是"代码封装"最直接的补法 |
| **字段级权限（`resource_scope`）** | 控制到字段可见/可编辑 | 比 RuoYi 更细。可作为 P2 |
| **API Token（AK/SK）** | 机器对机器访问，独立于用户 JWT | 与我们"开放 API"规划重合，直接借设计 |
| **后端 i18n** | 错误消息国际化，不只前端 | 我们全中文硬编码。开源后必需 |
| **UI 配置由后端下发** | 主题/布局偏好存后端 | 我们主题写死在前端 `theme.ts` |
| **分片上传** | 大文件断点续传 | 素材库场景需要 |

**糟粕（别抄）**

- **零代码/低代码野心是维护地狱**：在线表单设计器、页面设计器、仪表盘设计器三套引擎，任何一次 UI 框架升级都要改三套引擎；
- 30+ 个 `core/` 子包在 `ls` 时就劝退新人，需要靠文档补导航（我们开源初期应控制模块数）；
- Apache 2.0 + 附加条款的许可证写法容易被误读，开源许可应选标准 SPDX 文本。

**适用性评级：★★★★☆**（切片结构与 base_service 可搬，低代码引擎不碰）

### 2.5 JeecgBoot（SpringBoot + AntD Vue3，低代码）

**精华（选摘，注意它体量不适合我们）**

| 机制 | 说明 |
|------|------|
| **代码生成器四套模板**（单表/树/一对多/一对多树） | 生成即用，含菜单权限与 Excel 导入导出 | 我们可用 `python -m app.cli make:crud <table>` 做轻量版：只生成 router/schema/service/前端页面骨架，**不生成业务逻辑** |
| **声明式查询过滤器** | 页面配置 → 自动拼查询条件（相等/模糊/区间/包含） | 与"配置驱动列表页"是同一件事，见 §四.5 |
| **数据变更快照对比** | 记录每次变更内容并支持版本对比 | 我们审计只记动作。补「字段级 diff」即可对齐 |
| **OpenAPI AK/SK 授权** | 接口级授权 + 文档 | 与 zq 的 API Token 同构 |
| **JVXETable 行编辑表格** | 高密度编辑场景（ERP 类） | 我们的章节编辑可借鉴"行内编辑"交互 |
| **多数据库兼容** | MySQL/PG/Oracle/达梦/金仓… | 信创场景才需要，我们不做 |

**糟粕（别抄，且有实证风险）**

- **刚修完 SQL 注入（GHSA-jgwm/GHSA-xmw4/GHSA-g87f）**：根因是「字典过滤条件动态拼 SQL」。这直接说明**"在线配置查询条件"是长期安全负债**——你一旦把这个能力开放给使用者，注入面就永久存在。我们若做查询过滤器，**必须表达式白名单 + 参数绑定，绝不拼字符串**；
- 体积巨大：单体/微服务双模式 + 工作流 + 报表 + 大屏 + AI 平台，`git clone` 与构建成本极高，开源项目的"第一印象成本"被拉高；
- `create_all` 与 Alembic 并存容易造成生产表结构漂移；
- 低代码平台的"在线建表"会让**代码与库结构脱钩**，对一个要长期维护的开源项目是毒药。

**适用性评级：★★☆☆☆**（只借代码生成器的"模板化"思路与字段 diff，其余不碰）

## 四、融合方案（按维度落地）

> 原则：**只搬机制，不搬代码**。Python/React 与 Java/Go 生态不同，照抄实现等于制造第二套风格。

### 4.1 性能：先能测，再优化

**Step 1｜建立基线（没有数字就不要谈优化）**

| 指标 | 目标 | 工具 |
|------|------|------|
| 关键接口 P95 | 列表 < 200ms、详情 < 150ms、写入 < 300ms（本地 MySQL，10 万行量级） | `pytest-benchmark` 或自写 `scripts/bench.py` |
| 列表接口 N+1 | **0**（SQL 条数 ≤ 3） | SQLAlchemy `event.listen("before_cursor_execute")` 计数断言 |
| 首屏（后台） | LCP < 1.5s、入口 JS < 200KB gzip | `vite build --report` + Lighthouse |
| 慢查询 | > 200ms 记录并打点 | 中间件 + `logging` |

**Step 2｜治理 N+1（当前最实在的收益）**

- 列表接口统一走 `selectinload`，禁止在循环里访问懒加载关系；
- 加一条**架构守卫测试**（你已有 `test_arch_guards.py`，扩展即可）：任何 `admin_*` 列表端点执行期间 SQL 条数 > 5 即失败；
- 参考 RuoYi 的「连接池监视」思路，在 `SystemStatusPanel` 里暴露 `pool.checkedout()/overflow()` 水位。

**Step 3｜缓存分层（现有 `content_cache.py` 的规范化）**

| 层 | 内容 | 失效策略 |
|----|------|---------|
| L1 进程内 | 权限目录、菜单树、字典 | 版本号 + TTL 60s（已有菜单缓存可复用） |
| L2 Redis | 内容详情、首页聚合 | 写操作显式 purge（`content_purge.py` 已有） |
| 防击穿 | 单飞锁（singleflight） | Redis `SET NX` + 短 TTL |

**Step 4｜响应层**

- 列表接口**不返回正文**（`content`/`markdown` 字段），只回摘要 —— 这是最常见的隐性性能杀手；
- 强制 `limit ≤ 100`（服务端夹取，非前端校验）；
- gzip/br 交给 nginx（已有），FastAPI 侧加 ETag 即可。

**Step 5｜前端**

- 已有 `lazy()` 路由分割 → 补 `manualChunks` 把 antd / quill / echarts 拆出；
- 表格超 200 行启用 `virtual`；图片列表懒加载 + 缩略图 CDN 参数；
- 请求层做**去重与取消**（同 key 并发请求合并），`api/client.ts` 加一层即可。

### 4.2 安全：补「运营侧」，别动「密码学侧」

**已有的，写进 README 当卖点**（这几条对标项目里没有）：

- bcrypt 校验丢线程池、登录 dummy hash 防时序侧信道；
- 第三方密钥 Fernet 加密落库 + 掩码哨兵（`core/crypto.py`）；
- 限流对敏感端点 fail-closed（Redis 挂了宁可拒绝）；
- 审计留痕有测试守卫（`test_admin_audit_coverage.py`）。

**要补的（按优先级）**

| # | 能力 | 借自 | 做法 |
|---|------|------|------|
| S1 | **管理员在线会话 + 强制下线** | RuoYi 在线用户 / FastapiAdmin | `admin_session` 表（jti、IP、UA、最后活跃）；`GET /admin/sessions` + `DELETE /admin/sessions/{jti}`；改密/改权限时批量吊销 |
| S2 | **管理员强制 2FA** | — | `totp_service` 已有，加 `admin_require_totp` 开关：开启后未绑定的管理员登录即进绑定页 |
| S3 | **写操作幂等** | RuoYi `@RepeatSubmit` | 装饰器 `@idempotent(scope, ttl=5s)`，键 = 用户 + 方法 + 路径 + body 摘要；前端保留 `Idempotency-Key` 透传 |
| S4 | **登录验证码（滑块/拼图）** | FastapiAdmin | 仅对「连续失败 N 次」或「异地 IP」触发，不打扰正常登录 |
| S5 | **危险操作二次校验** | RuoYi 思路 | 删除/改价/改权限弹窗要求输入操作名或重新输密码；后端记录 `elevated_at`（5 分钟内有效） |
| S6 | **API Token（AK/SK）** | zq / JeecgBoot | 给开放 API 用；scope 化权限、可过期、可吊销、限流独立配额 |
| S7 | **CSRF 显式化** | — | refresh 走 cookie，需补 double-submit token 或 `SameSite=Strict` + Origin 校验（当前 `lax` 需评估） |
| S8 | **上传安全** | RuoYi XSS 过滤 | magic bytes 校验（不只靠后缀）、图片重编码（去 EXIF 与隐藏 payload）、SVG 禁用或净化 |
| S9 | **SSRF 收口** | JeecgBoot 白名单 | `image_proxy.py` / `third_party_fetch/` 必须复用 `AI_BASE_URL_ALLOWED_HOSTS` 同款域名白名单 + 禁止内网段解析 |
| S10 | **字段级权限**（P2） | zq `resource_scope` | 先只做「手机号/邮箱脱敏」一档，够用且成本低 |

**明确不做**：Casbin 策略引擎、CAS 单点登录、多租户隔离、OAuth 全家桶（除非有真实需求，否则是纯负债）。

### 4.3 易扩展：模块注册表 + 渐进式切片

**第一件（最高优先）：`module_registry.py`**

直接对标 FastapiAdmin 的 `ENABLED_MODULES`，但要更进一步——它只控制"加载不加载"，我们要让它成为**权限、菜单、路由、前端页面的单一事实来源**：

```python
ModuleDef(
    key="tutorial",
    label="教程",
    default_enabled=True,
    permissions=("tutorial:view", "tutorial:create", "tutorial:edit", "tutorial:delete"),
    routers=(admin_tutorials.router,),
    menu=MenuItem("/tutorials", "教程管理", "book", perm="tutorial:view"),
    page="Tutorials",              # 前端按此 key 找页面组件
    tables=("tutorials", "tutorial_nodes"),
    requires=(),
)
```

`router.py` / `admin_menu.py` / `rbac_catalog.py` 三处**从注册表派生**——现在它们靠人工对齐，正好合源。

**第二件：新模块用垂直切片（zq 的 `core/<domain>/`）**

不要全仓重构（253 个文件的迁移风险不可控），约定：

```
app/modules/<domain>/
├─ router.py      # 只做 IO、鉴权、参数
├─ service.py     # 业务规则
├─ models.py      # ORM
├─ schemas.py     # Pydantic
└─ README.md      # 模块边界与不变量
```

老模块（横切分层）保留，**新模块一律用切片**，并在 `docs/03-开发/` 里写明"两种结构并存是有意的，迁移按需"。

**第三件：`base_service`（zq 的 base_* 三层）**

把重复了 30 遍的东西收上来：

```python
class BaseService(Generic[M, C, U]):
    async def list(self, q: QuerySpec) -> Page[M]        # 分页 + 筛选 + 排序 + 数据权限
    async def get(self, id: int) -> M
    async def create(self, payload: C, actor: User) -> M
    async def update(self, id: int, payload: U, actor: User) -> M
    async def delete(self, id: int, actor: User) -> None  # 软删 + 审计 + 缓存失效
    async def batch(self, ids: list[int], op: BatchOp) -> Affected
```

关键设计：`delete/create/update` 内部**强制触发审计与缓存失效**，让"忘记写审计"在类型层面不可能发生——这比现在的 `test_admin_audit_coverage.py` 事后检查更根本。

### 4.4 易维护：把"约定"变成"契约"

| 动作 | 说明 | 收益 |
|------|------|------|
| **OpenAPI → TS 类型** | `openapi-typescript` 生成 `types/api.d.ts`，替换手写 `types/` | 前后端字段漂移归零，删掉一整类 bug |
| **错误码字典** | `error_codes.py` 集中定义 + 前端 `messages.ts` 映射 | 现在错误文案散在 service 里，无法国际化也无法测 |
| **迁移规约 + squash** | 79 个迁移压成 1 个 baseline + 增量；命名 `YYYYMMDD_动词_对象` | 新用户 `alembic upgrade head` 从 79 步变 2 步 |
| **模块 README 模板** | 每个模块写：职责 / 不变量 / 依赖 / 数据表 | 新人可导航，AI 也更容易改对 |
| **ADR 目录** | `docs/adr/0001-为什么不用-Casbin.md` | 开源项目最重要的"为什么"，比"怎么做"更能建立信任 |
| **测试分层门槛** | 单测 / 接口 / 架构守卫 / 契约 / 性能各一层，CI 分 job | 现有 935 用例已很强，缺的是**性能层与契约层** |

### 4.5 组件封装（前端）：从"复用 26%"到"配置驱动"

**现状**：50 个页面 19125 行；`useCrudList` 只被 13 个页面用；24 个页面手写 `<Table>`；`AiModels/index.tsx` 1231 行、`Tutorials/Edit.tsx` 1016 行 —— 单体页面是维护成本的主要来源。

**要做的三个抽象**（对标 RuoYi 的 `dict-tag`、Jeecg 的声明式组件，但用 React 的写法）：

```
<ResourceListPage
  resource="tutorial"                     // 决定 API 前缀与权限前缀
  columns={tutorialColumns}               // 声明式列（含 render / 权限 / 宽度）
  filters={tutorialFilters}               // 声明式筛选（类型驱动控件）
  actions={[createAction, batchDelete]}   // 权限自动过滤
  rowKey="id"
/>
```

| 抽象 | 解决什么 | 覆盖页面 |
|------|---------|---------|
| `ResourceListPage` | 列定义、筛选、分页、批量选择、空态、错误态、权限按钮 | 20+ 列表页 |
| `EntityFormPage` / `FieldStack` | 表单布局、字段渲染、校验、脏检查、离开确认、保存回滚 | 15+ 编辑页 |
| `DictSelect` / `UserPicker` / `DeptTreeSelect` | 字典与实体选择组件（RuoYi 的字典组件等价物） | 全站枚举 |

**关键约束**：抽象层必须允许"逃生" —— 复杂页面（`Tutorials/Edit` 的章节树、`AiModels` 的多 Tab 配置）继续手写，抽象只覆盖 80% 的规整场景。**不要为了统一而统一**，那是低代码平台的陷阱（见 JeecgBoot 的糟粕）。

### 4.6 代码封装（后端）：声明式能力

| 能力 | 借自 | Python 实现 |
|------|------|------------|
| **声明式导出** | RuoYi `@Excel` / Jeecg autopoi | dataclass 字段注解 → `openpyxl` 生成；支持列宽、枚举翻译、时间格式 |
| **声明式导入** | 同上 | CSV/XLSX → Pydantic 校验 → 逐行错误报告（返回行号 + 字段） |
| **查询过滤器** | Jeecg 查询过滤器 | **只允许白名单字段 + 运算符枚举 + 参数绑定**，绝不拼 SQL（Jeecg 刚因此修复三个 GHSA） |
| **轻量代码生成** | Jeecg 四套模板 | `python -m app.cli make:crud <table> --with-menu`：生成切片目录骨架 + 权限码 + 迁移 + 前端页面骨架，**不生成业务逻辑** |
| **CLI 统一入口** | go-admin 多命令 | `app/cli.py`：`migrate / seed / doctor / make:crud / export` |

## 五、明确不抄的 7 件事

| # | 机制 | 出处 | 为什么不抄 | 我们的替代 |
|---|------|------|-----------|-----------|
| 1 | Casbin 策略引擎 | go-admin | 引入一套 DSL 换来的灵活性，我们用 `rbac_catalog` + 依赖注入已覆盖；多一层会破坏"权限码单一事实来源" | 现有 RBAC + 数据权限 |
| 2 | Shiro / Spring Security 那套过滤器链 | RuoYi / Jeecg | 生态不通用 | FastAPI 依赖 + 中间件 |
| 3 | 在线建表 / 低代码表单引擎 | JeecgBoot / zq | 代码与库结构脱钩，长期维护成本极高；且"动态拼查询条件"是注入温床 | 迁移文件 + 代码生成器 |
| 4 | 单/微服务双模式 | JeecgBoot | 单体够用，微服务是给别人的组织规模准备的 | 单体 + 模块注册表 |
| 5 | 多数据库方言适配 | FastapiAdmin / Jeecg | 我们会为 `ngram` 全文索引写三套方言，收益为零 | 明确只支持 MySQL 8 |
| 6 | 内置 IM / 工作流 / 报表 / 大屏 | Jeecg / FastapiAdmin | 开源项目失焦第一名；每个都是独立的长期产品 | 保持"内容中台"边界 |
| 7 | 把第三方密钥存表明文 | RuoYi 参数管理 | 已被我们 `core/crypto.py` 超越 | 加密落库 + 掩码哨兵 |

## 七、写进 README 的一句话总结

开源项目最缺的不是功能，是**让别人 30 秒内相信你靠谱**。建议在 README 放一张「工程能力对照表」，直接引用本文数据：

| 能力 | 我们 | 常见开源后台 |
|------|------|------------|
| 后端测试 | 935 用例，离线可跑 | 多为 0～数十 |
| 密钥存储 | Fernet 加密落库 + 掩码哨兵 | 明文存表 / 存配置文件 |
| 审计 | 写操作强制留痕，缺失即测试失败 | 有日志但无覆盖保障 |
| 限流 | 敏感端点 fail-closed | 有，但 Redis 故障即放行 |
| 权限 | 权限码/菜单/路由/守卫同源 | 菜单与权限手工对齐 |

这张表比任何功能清单都有说服力——**你的"感觉不行"，本质是这些事实从来没被摆出来过。**
