# 仅开源后台管理端 —— 切割方案

> 决策前提：只开源 `admin-frontend`（后台管理界面），不开源 `frontend`（PC 用户端）、`miniprogram`（小程序）、`prerender`（SEO 预渲染）。
> 评估日期：2026-10-29。本文是[开源就绪评估](开源就绪评估与功能路线.md) §二「方案 B」的展开执行版。

---

## 一、先纠正一个前提：后台离不开后端

这是这条路最容易踩空的地方。三个事实：

1. 后台前端调用的接口**全部在后端**（`/admin/*`、`/auth/*`、`/uploads/*`），没有后端它就是一堆不能点的页面；
2. 后端是**单体 FastAPI**，`router.py` 里 admin 路由与 C 端路由注册在同一个 app、共用同一份 SQLAlchemy 模型与会话；
3. 后台管理的数据（用户、教程、订单、积分）是 **C 端业务产生的**，剥掉 C 端前端不等于剥掉 C 端业务。

所以「只开源后台」的准确含义是：

> **开源 = 后台前端 + 支撑它的后端内核 + 对外内容 API；不开源 = 用户端界面、小程序、预渲染服务。**

代价是必须把后端拆出「内核 / 可选业务模块」两层，不能整包丢出去——否则别人拿到的是一个无法自解释的 253 文件单体。

## 二、证据：后台的真实接口足迹比想象中小

我把 `admin-frontend/src` 里所有请求路径抽了出来，去重后只有 60 余个，且只落在四类：

| 类别 | 路径 | 归属 |
|------|------|------|
| 管理接口 | `/admin/tutorials`、`/admin/users`、`/admin/rbac/*`、`/admin/settings` … | 30 个 `admin_*.py` |
| 认证接口 | `/auth/login`、`/auth/me`、`/auth/logout`、`/auth/totp/*` | `auth.py`（仅用到登录态与 2FA 部分） |
| 上传接口 | `/uploads/image`、`/uploads/file` | `uploads.py` + 存储层 |
| 基础数据 | `/categories`、`/settings`（读取） | `categories.py`、`settings.py` |

**完全没有用到**：`home.py`、`sitemap.py`、`llms_txt.py`、`indexnow_key.py`、`images.py`、`payments.py`（C 端支付回调）、`stats.py`（C 端埋点）。

结论：**接口切割很干净，难的是模型与服务的共享**（43 张表里后台直接管到 30 张以上）。所以切割动作应发生在「模块装配层」，而不是逐个接口搬文件。

## 三、四个结构性卡点（不解决，开出去就是半成品）

### 卡点 1：用户从哪来？（最致命，且最容易被忽略）

后台管的是 C 端注册用户。只开源后台后：

- `用户管理` 页能新增用户（`admin_user_create` 已有），但**没有注册入口**；
- `积分流水` 页永远是空表——没有签到/消费行为产生流水；
- `实名审核` 页没有待审数据；
- `评论/举报/反馈` 三个 UGC 页面全是空列表。

一个所有列表都空的 demo，是劝退第一名。

**必须二选一：**

| 方案 | 做法 | 代价 |
|------|------|------|
| **A. 保留最小 C 端 API**（推荐） | 只保留注册/登录/邮箱验证码/个人资料/积分查询这几个 API，**不发前端页面**。后台从此有真实数据流 | 需要标注「这些接口是给你自己的前台用的」 |
| B. 造种子数据 | `seed_demo.py` 生成 50 个用户 + 200 条内容 + 订单流水 | 只能看不能动，且首次接触会觉得"假" |

**建议 A + B 并行**：API 保证真实可用，种子数据保证开箱有画面。

### 卡点 2：前端路由硬编码，删模块要改代码

> **2026-10-30 进展**：已把路由从 `App.tsx` 抽成 `routes/adminRoutes.tsx` 表驱动，
> 并加 `backend/tests/test_admin_routes.py` 跨语言守卫（权限码是否存在、每条路由是否挂守卫、
> 路由与菜单是否同一组权限码）。删模块从「改核心文件 `App.tsx`」降为「删表里的一行」。
> 下文的「约定式自动注册」仍是后续目标——那时连这一行都不用写。

`App.tsx` 167 行里手写了 38 个 `lazy()` 与全部 `<Route>`。而侧边栏菜单是**后端下发**的（`admin_menu.py`）——菜单能配、路由不能配。

后果：使用者想删掉「支付/积分/兑换码」三个模块，除了后端关接口，还得改前端 `App.tsx`。对开源项目，"删一个模块要动核心文件"是二次开发体验的硬伤。

**解法：约定式路由 + 菜单 key 映射**

```ts
// 页面按目录约定自动注册，新增/删除模块不再动 App.tsx
const pages = import.meta.glob('./pages/*/index.tsx')          // 或 List/Edit 双页
const routes = menuLeaves.map(leaf => ({ path: leaf.path, element: pages[leafKey] }))
```

配套要求：菜单项里带上 `path`（已有）与 `page` 标识（需补），路由表只做「菜单 → 页面组件」的查表。

### 卡点 3：后端是横切分层，没有模块边界

现状：`api/`（30+ 文件）、`models/`（30 个）、`services/`（80+ 个）三层横切，一个「教程」功能散落在 3 个目录 6 个文件里，且 `admin_tutorials.py` 与 `tutorials.py` 共用 `tutorial_service`。

后果：无法回答「关掉支付模块」这个动作——支付散在 `admin_payments`、`admin_payment_settings`、`payment_service`、`payments/`、`payment.py` 模型、`setting_definitions` 里。

**解法：不搬文件，加一层模块注册表**（成本比重构成 `modules/` 目录低一个数量级）

```python
# app/module_registry.py —— 单一事实来源，与 rbac_catalog / admin_menu 合并
ModuleDef(
    key="payment",
    label="支付与套餐",
    default_enabled=False,          # 开源默认关，文档教怎么开
    permissions=("payment_product:*", "payment_order:view", "payment_setting:*"),
    routers=(admin_payments.router, admin_payment_settings.router),
    menu_group="operations",
    requires=("user",),             # 依赖声明，关闭用户模块则本模块自动禁用
    tables=("payment_order", "payment_product"),
)
```

`router.py`、`admin_menu.py`、`rbac_catalog.py` 三处全部改为**遍历注册表生成**——这三者现在已经"手工对齐"，正好借这次机会合成一份。**这本来就是你这个项目最大的架构亮点，开源前把它做实，就是最好的技术叙事。**

### 卡点 4：三方能力无 Mock，空跑即报错

后台处处依赖外部服务：上传 → 腾讯云 COS；充值套餐 → 支付网关；AI 写作 → DeepSeek；图片搜索 → Pexels/Pixabay；邮件 → SMTP；登录 → 微信/短信。

后台-only 版本必须做到 **"一个 Key 都不配，也能完整点一遍"**：

| 能力 | 必做的降级 |
|------|-----------|
| 存储 | `local` provider 落卷（`/data/uploads`），默认选中 |
| 支付 | `mock` provider：订单可直接标记已支付，用于演示充值流程闭环 |
| AI | `mock` provider：返回固定文本，页面可点、成本零 |
| 邮件 | 控制台输出模式（`MAIL_PROVIDER=console`），验证码打到日志 |
| 短信 | 同上，`console` 模式 |
| 图片搜索 | 未配 Key 时隐藏该 Tab，而不是报 403 |

## 四、推荐形态：把「后台」讲成「内容中台」

后台-only 最难的是价值主张：**别人为什么要一个没有前台的 CMS？**

答案不是"这是个后台模板"，而是：

> **一个自带 RBAC、审计、审核、AI 写作的内容中台。你用它的后台管内容，用它的 API 渲染你自己的站点——WordPress 上前台绑定、Strapi 上后台单薄，这个两头都够。**

这条路成立的前提很硬，但你**已经具备了大半**：

- C 端只读 API 齐全：`/tutorials`、`/resources`、`/nodes`、`/tools`、`/plugins`、`/home`、`/sitemap`、`/llms.txt`；
- SEO 能力内建（sitemap / IndexNow / 百度推送 / llms.txt）—— 这是绝大多数开源 CMS 没有的；
- 富文本编辑器 + AI 写作是后台侧能力，与前台无关；
- RBAC 到按钮级 + 审计留痕，是"多人协作运营"的门槛能力。

**要补的只有一环：把内容 API 从"C 端页面的附属"提升为"一等公民"** —— 独立的版本前缀（`/api/v1/content/*`）、独立的 OpenAPI 文档页、一个 20 行的 `curl` 示例、以及一个「30 分钟渲染自己的前台」教程。

参照物选 **Strapi / Directus / Payload**（内容中台），不要选若依 / vue-element-admin（后台模板）——后者的赛道已经卷死，而且会让人误以为你这是"CRUD 生成器"。

## 五、模块切割清单

按「开源默认是否启用」分三档。**代码全部保留，靠注册表开关控制**，不做物理删除——这样上游改动与下游裁剪不冲突。

### 第一档：内核，必开（约 40% 代码量）

| 模块 | 后端 | 前端 | 理由 |
|------|------|------|------|
| 认证 / 管理员登录 / 2FA | `auth.py`（登录态部分） | `Login` `Profile` | 地基 |
| RBAC（角色/权限/部门） | `admin_rbac.py` | `Roles` `Departments` | **最大卖点** |
| 操作审计 | `admin_audit.py` | `AuditLogs` | 卖点，且有测试守完整性 |
| 菜单下发 | `admin_menus.py` | `AdminLayout` | 已做对，保留 |
| 用户管理 | `admin_users.py` | `Users` | 中台必须有主体 |
| 系统设置 | `admin_settings.py` + 4 个独立设置模块 | `Settings` `LoginSettings` `MailSettings` | 地基 |
| 上传 / 存储 | `uploads.py` + **新增 local provider** | 编辑器内联 | 没有它富文本不可用 |
| 分类 | `categories.py` | `Categories` | 内容组织 |
| 看板 / 系统状态 / 定时任务 | `admin_ops.py` | `Dashboard` `ScheduledJobs` | 运维第一屏 |
| 公告 / 消息通知 | `admin_announcements.py` `admin_messages.py` | `Announcements` `Messages` | 运营触点 |

### 第二档：内容与运营，默认开（约 45%）

| 模块 | 默认 | 说明 |
|------|------|------|
| 教程（章节树 + 富文本 + 发布流转） | ✅ | **保留为「内容类型范例」**，结构最完整，别人照抄就能加自己的类型 |
| 知识百科（树形节点） | ✅ | 第二种形态范例（树 vs 线性），建议保留 |
| 内容审核 / 评论 / 举报 / 反馈 | ✅ | UGC 平台必备，通用性强，且是"后台专业度"的体现 |
| 素材库 / 图片搜索 | ✅ | 后台效率工具，AI 图与图库导入是亮点 |
| AI 模型管理 / AI 写作 | ✅（无 Key 时降级） | 差异化卖点，但不能因缺 Key 报错 |
| 搜索词分析 | ✅ | 依赖 `search_log`，空表时展示引导文案 |
| 资源 / 在线工具 / 扩展推荐 | ⚠️ 可选 | 业务味重（网盘链接、下载计数、GitHub 抓取），建议**默认关**，作为"如何接入自己的内容类型"的第二个例子 |

### 第三档：电商与增长，默认关（约 15%）

| 模块 | 默认 | 说明 |
|------|------|------|
| 支付套餐 / 订单 / 支付渠道 | ❌ | 通用内容站用不上；开启后必须走 mock 网关 |
| 积分流水 / 兑换码 | ❌ | 依赖 C 端行为产生流水，单独开源时是空壳 |
| 实名审核 | ❌ | 强合规场景，通用性低 |
| 邀请关系 / 小程序 / 预渲染 | ❌ | 直接不进仓库 |

> **默认关闭 ≠ 不交付**。文档里给一张「模块开关表」，告诉使用者 `enabled=True` 一行就能打开，并说明需要配什么。这比"删掉了"有价值得多。

## 六、仓库形态

### 6.1 目录

```
ai-cat-admin/                     # 新仓库（不要把现有仓库直接公开）
├─ backend/
│  ├─ app/
│  │  ├─ core/           # 配置、异常、日志、数据库、Redis
│  │  ├─ module_registry.py    # ★ 新增：模块单一事实来源
│  │  ├─ providers/            # ★ 新增：storage / mail / sms / payment / ai 抽象
│  │  ├─ api/ models/ services/  # 保持现有横切分层，不重构成 modules/
│  │  └─ ...
│  ├─ alembic/
│  └─ tests/
├─ admin/                # 原 admin-frontend，去掉 base=/admin 的强绑定说明
├─ deploy/
│  ├─ docker-compose.yml        # 只留 app + mysql + redis + nginx 四服务
│  └─ .env.example              # 收敛到 10 项以内
├─ examples/
│  └─ frontend-minimal/         # ★ 20 行取内容 API 渲染的最小前台示例
├─ docs/
├─ LICENSE
└─ README.md
```

**关键点：新仓库、单次 initial commit。** 现有仓库 335 次提交里含 `backups/*.sql`、日志、`.env` 等，清洗历史不如重生。

### 6.2 部署档位

`docker-compose.yml` 从 29 KB / 7 服务压到 4 服务，去掉 `prerender`（C 端 SEO 用）、`umami`（统计）、`watchdog`（可用宿主 cron 替代）。

### 6.3 环境变量收敛

104 → 目标 **≤ 10 项**：

```
必需：SECRET_KEY / MYSQL_* / REDIS_PASSWORD / ADMIN_PASSWORD / SITE_BASE_URL / STORAGE_DRIVER
可选：SMTP_* / AI_KEY（也可后置到后台配置）
```

其余全部迁入 `SystemSetting`（后台可视化配置，已验证可行）——`check_env_consistency.py` 之后可以改成检查"哪些还留在 env"。

## 八、README 必须回答的四个问题

开源后台的读者只关心四件事，缺一个就走：

1. **这是什么？** —— 一句话：自带 RBAC / 审计 / 审核 / AI 写作的 AI 内容中台。配 6 张截图。
2. **怎么跑起来？** —— 一条 `docker compose up`，首屏给命令，不给 104 个变量。
3. **和 Strapi / Directus 有什么不同？** —— 对比表，落在"中文内容运营 + SEO 内建 + 按钮级权限"三点。
4. **我的数据在哪？** —— local 存储 + MySQL 导出 + 后台一键备份，明确"不锁定"。

## 九、需要你拍板的两件事

1. **内容 API 是否独立成 `/api/v1/content/*`**：独立 = 定位清晰、可长期兼容；不独立 = 省 2 天但和后端内部接口混在一起，以后不敢改。
2. **支付/积分是否进仓库**：进 = 功能完整但需维护 mock 网关；不进 = 干净但"充值套餐"页面要一并删掉。
