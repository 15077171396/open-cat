### 2.2 为什么 FastAPI 而非 Django REST Framework

| 维度 | FastAPI | Django REST Framework |
|------|---------|----------------------|
| 异步支持 | 原生 async/await，天然适配 AI API 异步调用 | 异步支持较弱，需额外配置 |
| 性能 | 接近 Node.js / Go 水平 | 中等 |
| 类型安全 | Pydantic 模型，自动校验 | Form / Serializer，稍繁琐 |
| API 文档 | 自动生成 Swagger / ReDoc | 需第三方插件 |
| 学习成本 | 低，核心概念清晰 | 中，全家桶概念多 |
| 轻量度 | 框架极轻，按需引入 | 重，自带 admin / ORM / template |

> **结论**：本项目前后端分离，后端只提供 API，且核心场景涉及 AI API 异步调用，FastAPI 是最优选择。**Django 自带的 admin 在本项目中无用**——管理端需要与前台共享设计语言与业务逻辑，自建 React 管理端更合适（见 [2.5](#25-为什么自建管理端而非复用-django-admin)）。

### 2.3 为什么 DeepSeek 作为默认模型

| 维度 | DeepSeek | OpenAI GPT | 通义千问 |
|------|----------|-----------|---------|
| 价格 | 极低（约 GPT-4 的 1/100） | 高 | 中 |
| 能力 | 接近 GPT-4，代码/推理强 | 最强 | 强 |
| 国内访问 | 直接可用，无需代理 | 需代理 | 直接可用 |
| API 兼容 | OpenAI 兼容格式 | 原生 | 兼容 |
| 中文能力 | 优秀 | 良好 | 优秀 |

> **结论**：DeepSeek 成本极低、国内可直接访问、API 与 OpenAI 兼容，是当前阶段最优选择（故为 `DEFAULT_AI_MODEL`）。
>
> **多模型适配层**：`services/ai/openai_compat.py`（协议实现）+ `factory.py`（注册表路由）
> 已接入 **deepseek / openai / qwen** 三家 —— 三家都是 OpenAI 兼容协议，故共用一份实现，
> 各家只声明 `base_url` / API Key / 默认模型差异。工具的 `ai_config.model` 填 Provider 名即可切换。
> ⚠️ 未配置 API Key 的 Provider 被调用时**明确报错**，不会静默回退到其它模型（换模型会改变成本与输出质量）。

### 2.4 为什么 MySQL 而非 PostgreSQL

| 维度 | MySQL 8.0 | PostgreSQL 16 |
|------|-----------|---------------|
| 运维生态 | 国内运维更熟悉，云数据库支持广 | 稍小众 |
| JSON 支持 | JSON 类型（8.0+ 完善） | JSONB（更强大） |
| 全文搜索 | FULLTEXT + ngram 分词器（中文可用） | 原生支持更好 |
| 性能 | 简单读写场景优秀 | 复杂查询更优 |
| 成本 | 云 RDS 更便宜 | 稍贵 |

> **结论**：以简单读写为主，MySQL 运维生态成熟、云服务成本低。
>
> ✅ **已落地**：中文全文检索走 **MySQL 8 内置 ngram 全文索引**（迁移 `0028` / `0032`），
> 并按 `search.py` 的口径保留 `LIKE` **回退**——实测证明 ngram 在部分查询串/索引缺失情况下会失败，
> 回退不是「还没升级」。刻意未引入 Elasticsearch：对单机 2 核 4G 是重资产。
>
> 注：项目已引入 PostgreSQL，但**仅供 Umami 访问统计使用**，与应用库完全隔离，不参与业务。

### 2.5 为什么自建管理端而非复用 Django Admin

管理端需求已远超通用后台能力：**RBAC 组织架构**、**教程章节树编辑**、**富文本编辑器（自定义 blot）**、**第三方资料一键导入**、**积分与兑换码管理**、**手写 SVG 数据看板**。这些无法通过配置通用后台达成，且需要与前台共享类型与设计令牌，故自建独立 React 管理端。

## 四、关键技术决策

### 4.1 大文件走网盘链接而非对象存储

| 维度 | 网盘链接方案（采用） | 对象存储方案 |
|------|-------------------|-------------|
| 服务器带宽 | 零压力 | 需承担下载带宽 |
| 存储成本 | 零（网盘免费） | 按存储量 + 流量计费 |
| 用户体验 | 需跳转网盘，可能限速 | 直接下载，体验好 |
| 实现复杂度 | 低（只存链接） | 高（签名 URL + 防盗链） |
| 适合场景 | 大文件、早期阶段 | 付费产品、小文件 |

> **结论**：大文件（如 12.5GB 的模型/工具整合包）不进入自有存储，仅在 `resource_netdisk_links` / `tutorial_netdisk_links` 保存链接 + 提取码。对象存储仅用于教程封面、用户头像、正文图片等小文件。
>
> **代价与边界**：用户体验受网盘限速影响，且链接失效需人工维护。后续若推出高价值付费资源，可对该部分改用对象存储 + 签名下载。

### 4.2 非自增 ID

**全库主键使用 10 位随机数字**（`secrets.randbelow(9_000_000_000) + 1_000_000_000`），非自增。

| 方案 | 问题 |
|------|------|
| 自增 ID | 可被枚举爬取（遍历 `/tutorials/1..N` 即可拖库），且暴露业务规模 |
| UUID | 索引膨胀、可读性差、URL 冗长 |
| **10 位随机数字（采用）** | 枚举成本极高，URL 长度与可读性接近自增 ID |

> 代价：失去自增带来的天然时序性，排序需显式依赖 `created_at` / `published_at`。

### 4.3 免费时长用「自然时间窗口」而非「累计时长」

```
判定：now - free_started_at >= FREE_TIME_LIMIT(10800s)
```

| 方案 | 行为 | 问题 |
|------|------|------|
| 累计 `free_used_seconds` | 只在实际阅读时累加 | 可被「挂着不看」规避，也可被上报伪造 |
| **自然时间窗口（采用）** | 注册即开始倒计时，离线也计时 | 用户「注册了没用」也会消耗额度 |

> **取舍**：选择自然窗口是因为它**不依赖客户端上报的可信度**——累计模式的安全边界完全建立在「前端每 10 秒诚实上报」之上，而这是可以伪造的。自然窗口的判定在后端独立成立。
>
> ⚠️ 因此 `free_used_seconds` 仅作为**实际学习时长统计**保留，不参与任何权益判定。看板转化率分母也同步使用自然时间口径。

### 4.4 Redis 全链路降级

**原则：Redis 是加速层，不是正确性依赖。**

| 场景 | 降级行为 |
|------|---------|
| 缓存读失败 | 直查 DB（如首页聚合、热门资源、精选插件、看板统计） |
| 防刷标记失败 | 放行（不阻断正常用户） |
| 日限额检查失败 | fail-open（不阻断 AI 调用） |
| 登录锁定检查失败 | fail-open（不阻断登录主流程） |

> 后果：Redis 故障时公开接口**不会 500**，代价是短时失去缓存加速与防刷能力。这是「可用性优先于防护」的自觉选择。

### 4.5 AI 调用的超时、降级与限额

```
超时：30s（AI_TIMEOUT_SECONDS）
重试：最多 2 次（AI_RETRY_COUNT）
响应校验：限流/风控（HTTP 200 + {"error":...}）与空内容 → 明确的 503 业务错误，不落 500
单用户日限额：50 次（ai_daily:{user_id}:{YYYYMMDD}）
输入约束：字段 ≤ 20 个，单值 ≤ 2000 字符
```

> ✅ **全站护栏已落地**：除单用户限额外，全站有 `AI_GLOBAL_DAILY_LIMIT` /
> `AI_GLOBAL_MONTHLY_LIMIT` 两道**全局成本护栏**（超限即拒绝并给出可读原因），
> 管理端看板有「AI 用量与成本护栏」区块（按模型归因用量与费用）。
> 仍未实现的是**主动告警**：护栏是「被触发才可见」，用量异常上涨本身不会推给运维。

### 4.6 积分扣费的原子性

**统一原则：条件原子更新 + 回读真实余额写流水。**

```sql
UPDATE users SET points = points - :cost WHERE id = :uid AND points >= :cost
```

- 影响行数为 0 即余额不足，**不做「读-改-写」**；
- 扣减成功后 `db.refresh(user)` **回读真实余额**再写 `point_transactions.balance_after`，消除陈旧内存值；
- 管理端调整积分时对目标用户加 **行锁**（`SELECT ... FOR UPDATE`），与扣费的原子更新互斥；
- 教程购买采用「**先插购买记录（唯一约束）再扣费**」，唯一冲突即视为已购买，天然实现并发幂等。

### 4.7 SEO 采用动态渲染而非 SSR

| 方案 | 成本 | 效果 |
|------|------|------|
| SPA 改 SSR（Next.js） | 需重写整个前端 | 最彻底 |
| **动态渲染（采用）** | 新增一个容器 | 爬虫可抓，用户无感 |

Nginx 按 User-Agent 分流：国内爬虫（百度/360/搜狗/必应）→ `prerender:3000`（Chromium 渲染 SPA 后返回完整 HTML，结果缓存进 Redis）；Googlebot 除外（自带 JS 渲染能力）；普通用户 → 静态 SPA。

> ⚠️ **风险与已做的缓解**：Chromium 内存占用高，预渲染容器 `mem_limit` 现为 **1g**（不是早先记的 512m），
> 与 MySQL 争抢同一台 2 核 4G 机器的内存。爬虫高峰时若被 OOM 杀，爬虫会拿到 502 → 收录下滑。
> 已按本条建议落地**内存阈值降级**（`prerender/server.js` 的 `memoryPressure`：接近容器上限时
> 不起 Chromium、直接返回 SPA 壳，且**刻意不写缓存**，压力一解除下个请求就恢复渲染 ——）。
> **独立部署仍是可选优化**（阈值降级只是止血，没解决争抢本身）。

### 4.8 富文本以 blot 模型为唯一事实来源

Quill 的保存路径取 `editor.getSemanticHTML`，**只认 blot 模型**——任何「只改 DOM 不进 blot」的内容在保存瞬间静默丢失。

因此确立三条不可违反的约定：

1. 新增块级内容**必须**实现自定义 blot（tagName + className + `static value` / `static formats` 成对自洽）；
2. 块级格式**挂在行尾的 `\n`** 上，用 Delta 手工构造多行内容必须逐行给出换行；
3. 后台能力变更**必须同步前台两处**（`sanitize.ts` 白名单 + `custom.css` 排版），否则「后台能设、前台看不到」。

> 详见 [项目说明 6.4 节](../03-开发/项目说明.md#64-富文本编辑器管理端)。

### 4.9 定时任务：配置表驱动 + Redis 命令队列（而非写死 add_job）

调度器独立容器运行（`python -m scheduler.tasks`），任务采用「代码注册 handler × 库配置」双通道：

| 层 | 载体 | 说明 |
|----|------|------|
| 任务清单 | `services/scheduled_job_service.py::JOB_SPECS` | 周期默认值 / 超期阈值，唯一事实来源 |
| 任务体 | `scheduler/tasks.py::JOB_FUNCS` | id → handler，新增任务必须在此注册 |
| 可配置项 | MySQL `scheduled_job_configs` | 启停 / 周期，后台「定时任务」页直接改 |
| 生效状态 | Redis `ops:jobs:applied`（TTL 120s） | 调度器每 5 秒写回「我按哪份配置在跑」+ 存活心跳 |
| 手动执行 | Redis `ops:jobs:commands` | 「立即执行」命令队列，调度器每秒消费 |

> **为什么不用 `replace_existing` 热更新**：调度器每 5 秒比对配置指纹、变化才 add/remove——
> 无脑 `reschedule` 会重排 `next_run_time`，让每分钟任务永远等不到执行。
> 「立即执行」与调度触发共用进程内闩锁，同一任务绝不并发；调度器未运行时后台「立即执行」
> 直接 503 而非假装入队。详见 [项目说明 5.7](../03-开发/项目说明.md#57-定时任务)。

## 六、部署架构

**当前阶段：单机 Docker Compose · ✅ 已上线生产**（9 个服务：`nginx` / `prerender` / `migrate` / `app` / `scheduler` / `mysql` / `redis` / `umami` / `postgres`）

> 线上入口 `https://www.wdmao.cn`，**前置 EdgeOne CDN 回源到 `nginx:80`**（nginx 仅 80、无 TLS）。2026-10-15 线上实测：`/api/v1/health/deep` 返回 `status: ok`（MySQL 13.3ms / Redis 0.3ms，库版本与代码 head 一致）；爬虫 UA 下错误 URL 返回真 404、正文可抓取。完整实测见 [项目说明 § 1.4](../03-开发/项目说明.md#14-线上运行状态2026-10-15-实测)。

启动依赖链：

```
mysql (healthy) ──► migrate (completed) ──► app (healthy) ──► nginx
                                   └──────► scheduler
redis (started) ──┬────────────────────────► app
                  └────────────────────────► prerender (started) ──► nginx
umami (started) ──────────────────────────► nginx
```

> nginx 对 prerender / umami 只要求 `service_started`（不要求 healthy）——增强件挂了只少功能，不能拖垮主站。

服务器建议：2 核 4G 起步（**推荐 4 核 8G**，因 MySQL + Redis + Chromium + 前端构建产物共存）。

> 完整部署步骤、运维命令、备份恢复与故障排查见 [部署说明书](../04-运维/部署说明书.md)。

## 七、扩展性规划

### 阶段一：MVP（当前）

- 单机 Docker Compose，MySQL + Redis 单实例
- FastAPI 2 workers
- 网盘链接方案（零存储成本）
- DeepSeek 默认模型

### 阶段二：成长期（1 万 - 10 万用户）

| 动作 | 触发条件 |
|------|---------|
| 数据库迁移到云 RDS（主从） | 单机 MySQL 成为瓶颈或需要高可用 |
| FastAPI 水平扩展 + 负载均衡 | 单机 CPU 持续 > 70% |
| **预渲染服务独立部署** | 与 MySQL 争抢内存导致 OOM（**建议优先做**） |
| 对象存储接入 CDN | 图片成为 LCP 瓶颈时启用（现阶段不做；届时只需填 `COS_CDN_DOMAIN`，无需改代码） |

| AI 多模型负载均衡 | 单一供应商限额或成本失控 |

### 阶段三：成熟期（10 万+ 用户）

- K8s 容器编排
- 读写分离 + 分库分表（当前无 FK 约束、非自增 ID 的设计已为此预留）
- 消息队列（Kafka / RabbitMQ）异步化
- 高价值付费资源改用对象存储 + 签名下载
- 多级缓存体系
