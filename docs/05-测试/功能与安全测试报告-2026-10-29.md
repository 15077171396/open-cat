## 一、结论摘要

1. **工程基线整体健康**：后端 1815 个用例全绿（26.6s）、管理端 300 个用例全绿、两端类型检查 / ESLint / 生产构建全部通过、5 个仓库守卫脚本 4 个通过、深度健康探针显示 MySQL + Redis + 迁移版本一致。
2. **但存在 2 个"测试全绿、功能全挂"的缺口**：`POST /api/v1/reports`（提交举报）与 `POST /api/v1/users/favorites`（收藏教程）稳定返回 500，属于用户端高频操作。两者根因同类——**异步 SQLAlchemy 会话里的隐式 IO（延迟加载未投影列）**，现有 1815 个用例用的是内存 `fake_db`，不模拟 deferred / server_default 语义，因此完全没拦住。**（当日已修复并补齐回归测试，见第九节）**
3. **安全面表现良好**：22 项安全专项（鉴权、越权、令牌伪造、账号枚举、爆破锁定、限流、SQL 注入、XSS、SSRF、上传类型/大小/嗅探、支付回调验签、CORS）全部符合预期。
4. **文档可信度下降**：`docs/03-开发/项目说明.md` 自称"单一事实来源"，但与实测全面脱节（路径 198→205、操作 246→253、后端用例 1632→1815、管理端 194/19→300/36），`docs/README.md` 又是第三套数字（38 表 / 202 操作 / 165 路径）。

## 五、缺陷清单

> 严重级别：**P1 阻断**（核心功能不可用 / 门禁红）、**P2 高**（易触发错误或显著降低可维护性）、**P3 中低**（体验、契约、体积）。所有 P1 均已用 `git show HEAD:` 回溯，确认**存在于已提交的 master**，与工作区未提交改动无关。

### BUG-01【P1】提交举报必然 500，但数据已落库

| 项 | 内容 |
|----|------|
| 位置 | `backend/app/services/report_service.py:94-101`（`submit_report`） |
| 复现 | 用任意登录用户 `POST /api/v1/reports`，body `{"content_type":"tutorial","target_id":"11","reason":"spam"}` → **500 `{"code":500,"message":"服务器内部错误"}`**；再提交一次 → 400「您已举报过该内容」 |
| 日志 | `未处理异常: greenlet_spawn has not been called; can't call await_only() here`（`MissingGreenlet`） |
| 根因 | `db.add(report)` + `flush()` 后 `await db.commit()`，随即 `_report_to_dict(report)` 读取 `created_at`；该列是 `server_default=func.now()`，INSERT 后处于**未加载**状态，属性访问触发一次同步 SELECT。`expire_on_commit=False` 只让已加载属性不过期，救不了"从未加载"的服务端默认值列 |
| 影响 | 用户看到的永远是"举报失败"，实际已入库并占用唯一约束 → 用户重试得到"已举报过"，客服与审核台都无法从用户反馈定位；举报是内容治理的**唯一事后兜底通道**（项目已明确不接第三方机审），失效影响合规面 |
| 修复 | `flush()` 后 `await db.refresh(report)` 再 `commit`；或改为 `INSERT` 后 `select` 回读。同类风险需一并扫描：任何 `server_default` 列（`created_at`/`updated_at`）在 flush 后立即被读取的地方 |
| 回归 | 现有 1815 个用例全绿仍未拦截——需补一条"真实 ORM 语义"的用例（fake_db 应模拟未加载列/延迟列，否则这类缺陷永远测不出） |

### BUG-02【P1】收藏教程必然 500（其他类型正常）

| 项 | 内容 |
|----|------|
| 位置 | `backend/app/services/favorite_service.py:51-55`（`load_columns`）与 `:98`（`getattr(obj, spec.cover_attr)`） |
| 复现 | `POST /api/v1/users/favorites` `{"target_type":"tutorial","target_id":11}` → **500**；同样的调用 `resource` / `node` / `plugin` 均 200 且幂等 |
| 日志 | `MissingGreenlet ... [SQL: SELECT tutorials.cover_image FROM tutorials WHERE tutorials.id = %s]` |
| 根因 | `load_only(id, title, description)` 做了投影，但 `_FavoriteSpec.cover_attr="cover_image"`（`favorite_cover=True` 仅教程），`getattr` 命中未投影列 → 同步懒加载。`load_columns` 与 `cover_attr` 是两份各自维护的事实 |
| 影响 | 教程是平台最主要的收藏对象，"收藏"按钮必然失败；且失败伴随 keep-alive 连接被重置（见 OBS-02），前端重试会连带出现网络错误提示 |
| 修复 | `load_columns` 增加 `spec.cover_image`（当 `favorite_cover` 为真时）；更稳妥的做法是让 `load_columns` **由 `cover_attr` 派生**，杜绝两份清单漂移 |
| 回归 | 同上，需 fake_db 支持"投影列之外访问即抛错"的语义 |

### BUG-06【P3】响应模型声明了从未赋值的字段，所有响应带 3 个 `null`

`StatsResult` 声明 `total / categories / types`，但 `/users/stats`、`/users/learning/stats`、`/admin/dashboard`、`/admin/system-status`、`/admin/scheduled-jobs` 均只返回各自字段，另三键恒为 `null`；`ReportItem` 声明 `user_id / target_type / description`，而 service 产出的是 `reporter_id / content_type / target_id / detail`。因 `_Item` 配置了 `extra="allow"`（透传），功能未受损，但契约噪音会误导前端与第三方调用方，且增加响应体积。建议按端点拆分模型，或改用 `model_config = ConfigDict(extra="allow")` 且不声明无意义字段。

### BUG-07【P3】后端直连不返回安全响应头

直连 :8000 时 `X-Content-Type-Options` / `X-Frame-Options` / `Referrer-Policy` / `CSP` 全缺（`server: uvicorn` 亦暴露指纹）。生产链路由 `nginx.conf` 统一补齐（已核实 5 处 location 均显式声明），属纵深防御缺失：一旦绕过 nginx 或容器端口被误暴露，防护即失效。建议在 `main.py` 加一层轻量 header 中间件（CSP 可仍由 nginx 负责）。

### BUG-08【P3｜已确认非缺陷】首屏 chunk 偏大是刻意权衡

用户端 `index` 两个 chunk 466 KB / 726 KB、管理端 `antd-vendor` 1.25 MB 确实偏大，但 `frontend/vite.config.ts` 里有明确记录：曾经用 `manualChunks` 把 antd/rc-* 强制合并成一片（1005 KB），导致首页也要下载 Table/Upload/Tree 这些它从不渲染的组件；改为「放开、留在各自懒加载路由 chunk」后首屏从 1506 KB 降到 1045 KB（-31%），并接受「entry 随发版变化、老访客重下」的代价。阈值 900 KB 也是按此口径设的。

**结论：不改。** 若要继续优化，方向是减少首页真正依赖的 antd 组件，而不是把 chunk 重新合并。

### BUG-09【P3】测试环境数据过于单薄，限制验证深度

库中 13 个账号仅 2 个未注销；6 篇教程仅 2 篇已发布（其余 `status=updating`），资源 16 条。付费墙、列表筛选、分页、搜索、审核队列等只能验证"接口不报错"，无法验证"数据正确"。建议固化一份 `seed_qa.py`（覆盖免费/会员/已购买/已下架/草稿/违规待审各态）。

## 十一、第四轮：测试基建补强（按 §10.2 清单执行）

### 11.1 `fake_db` 补齐「未加载列」语义（原 §10.2 第一项，已完成）

这是上轮两个 P1 的**根因层**：内存仿真把 `server_default` 列当 `None`、也不模拟 `load_only`，
所以"漏 refresh / 漏投影"的代码在测试里永远绿。改动集中在 `tests/fake_db.py`：

| 语义 | 实现 |
|------|------|
| INSERT 后时间型 `server_default` 列未加载 | 权威行写入 UTC 时间，ORM 属性换成 `_Unloaded` 哨兵；读它就抛（等价 `MissingGreenlet`），只有 `refresh()` 或取回该列的 SELECT 才填真值。**删掉了原来那句 `obj.created_at = datetime.now()`** —— 正是它让 bug 隐形 |
| `load_only` 投影之外的列不可读 | 解析语句上的 `Load` 选项（`_AttributeStrategyLoad` + `column:*` 令牌），非投影列直接降级为哨兵 |
| 脏列判定不把哨兵写回库 | `dirty_columns` / `flush_dirty` 跳过 `_Unloaded`，避免仿真自己制造脏数据 |
| `seed()` 代表"库里已有的行" | 落库后立刻回填对象：测试把 seed 出来的对象直接传进 service 时，不会读到哨兵（生产里这些对象都是查出来的） |

**有效性验证（关键）**：把两处修复 `git stash` 掉之后——

- `tests/test_moderation.py` 有 **6 条**用例变红（此前带着 bug 也是绿的）；
- `test_qa_regressions.py` 的 3 条举报回归 + 3 条收藏回归同时变红；
- 恢复修复后 1827 条全绿。

同时把 `test_qa_regressions.py` 里自建的「会话替身」删掉了——**直接用 `MemorySession` 就是在测真实语义**，少一份重复实现。

## 十二、前端控制台告警修复：antd 静态 `message`（2026-10-29 晚）

### 现象

用户端资源详情页控制台刷满红字（`useFavorite.ts:90` 起），Issues 面板 65 项：

```
[antd: message] Static function can not consume context like dynamic theme.
Please use 'App' component instead.
```

### 根因

antd 在 `config-provider/index.js` 里有一条守卫：**只要页面上存在带 theme 的
`ConfigProvider`，调用静态 `message.xxx()` 就会告警**（`!existThemeConfig` 为假）。
静态方法自己挂 root，读不到 context，因此：

- 提示浮层用默认主题，与 `src/theme.ts` 的 token 不一致（切主题后尤其明显）；
- locale 对它无效（中文站弹出英文按钮）；
- 每次调用新挂一个 root，与 Modal/Drawer 的 z-index 关系不可控。

**注意这是 dev-only 告警**（`process.env.NODE_ENV !== 'production'` 时才跑），线上不刷控制台，
但"提示不走主题"是真实可见的体验问题。

### 修复方式：沿用管理端既有约定，而不是另造一套

排查时发现 **管理端早就解决过这个问题**（`admin-frontend/src/utils/toast.ts` + `ToastBridge`，
注释标着 MNT-07），用户端一直没跟上。所以没有新造轮子：

| 动作 | 说明 |
|------|------|
| 复制 `utils/toast.ts` | 与 `admin-frontend/src/utils/toast.ts` **逐字一致**（项目既有的"共享工具复制"惯例），导出 `bindToastInstance` + `toast` |
| `main.tsx` 加 `ToastBridge` | 在 `<AntApp>` 内把 `App.useApp().message` 绑给 toast，与 `monitoring` 初始化并列 |
| 迁移调用点 | **30 个文件、121 处** `message.xxx()` → `toast.xxx()`；import 从 `antd` 改为 `../utils/toast` |
| 保留 `App.useApp()` 的用法 | `ImageUploader` / `RightToolbar` 等本来就用 hook 取实例的，保持不动（它们本就没告警） |
| 加双份一致性守卫 | `monitoring-smoke.mjs` 新增 2 项：两份 `toast.ts` 必须逐字一致（41 → **43 项**） |

### 回归测试（先证明能红，再证明修好了）

`src/utils/toast.bridge.test.tsx`：

1. 在 `<ConfigProvider theme>` + `<AntApp>` 下**先调静态** `message.success()` →
   断言 `console.error` 确实出现 `Static function can not consume context`（**基线**，
   证明这条用例抓得住该问题）；
2. 再调 `toast.success()` → 断言不再出现该告警。

`src/utils/toast.test.ts`：绑定后转发到主题化实例、方法 `this` 绑定正确（antd 实例方法依赖 `this`）。
